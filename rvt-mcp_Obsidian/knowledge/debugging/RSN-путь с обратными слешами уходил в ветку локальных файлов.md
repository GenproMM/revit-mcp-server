# RSN-путь с обратными слешами уходил в ветку локальных файлов

**Дата обнаружения:** 2026-09-17  
**Где:** `_is_revit_server_path` в `tools/worksharing_tools.py` и `revit_mcp/worksharing.py`

## Симптом

Агент на рабочих местах отвечал: «MCP-bridge не может открыть RSN:// путь напрямую, нужно открыть модель вручную».

Этой строки **нет в репозитории** — её сочиняет модель, когда инструмент возвращает ошибку. Поэтому текст жалобы не указывал на место и вёл к ложному выводу, будто Revit Server не поддерживается в принципе.

## Две независимые причины

### 1. Полный RSN-путь всё равно шёл в журнал

`_resolve_revit_server_path` **всегда** читал `//srv-dfs/BIM/.../RevitModelLiteProcessorJournal.json`, даже когда путь уже содержал сервер и папку. Недоступная шара (VPN, права, сеть) превращала полностью корректный `RSN://сервер/папка/Модель.rvt` в `FileNotFoundError` до того, как запрос доходил до Revit.

Журнал нужен только для сокращения вида `RSN://Модель.rvt`, где по имени файла ищется расположение. Полный URI — это ровно то, что потребляет сам Revit, и посредник ему не нужен.

### 2. Написание с обратными слешами не распознавалось как RSN

Проверка была:

```python
file_path.strip().lower().startswith("rsn://")
```

Пользователи копируют пути из Windows-диалогов и получают `RSN:\\srv\Projects\Model.rvt`. Такой путь не проходил проверку, уходил в ветку локальных файлов, и там `os.path.exists()` закономерно объявлял модель отсутствующей.

**Тонкость, на которой я сам ошибся.** Первая гипотеза была «неверный порядок: сначала срезаем схему, потом нормализуем разделители». Неверно. Настоящая причина считается на бумаге:

```
"RSN:\\srv\Projects\Model.rvt".replace("\\", "/")  →  "RSN:/srv/Projects/Model.rvt"
```

Два обратных слеша схлопываются в **один** прямой. Префикс `rsn://` не совпадает, а срез `[len("rsn://"):]` промахивается на символ. Количество разделителей после двоеточия зависит от того, как путь экранировали по дороге, и полагаться на него нельзя.

## Решение

```python
file_path.strip().lower().replace("\\", "/").startswith("rsn:/")
```

Один слеш как минимум. Разбор на сегменты — через `split(":", 1)`, а не через срез фиксированной длины.

Исправлено **с обеих сторон моста**: `_is_revit_server_path` существует независимо в `revit_mcp/` и в `tools/`, и расхождение между ними породило бы новый класс багов, где CPython считает путь серверным, а IronPython — локальным.

## Урок про инструменты

Тестовый литерал с обратными слешами **трижды** получился неверным при записи через вложенный heredoc (`python - <<'EOF'` внутри Bash): каждый уровень съедает свой слой экранирования. Файлы с обратными слешами надо писать инструментом Write.

Баг с распознаванием поймал **тест, а не чтение кода** — причём тест на функцию, которую я только что написал сам.

## Проверка

`tests/unit/test_revit_server_paths.py` покрывает оба написания, сокращённую форму, обход журнала при полном RSN URI и проброс локальных путей без изменений.

Для сокращения `RSN://Модель.rvt` журнал обязан читаться строго по Windows UNC-пути:
`\\srv-dfs\BIM\01_Ресурсы плагинов\10_Облегченные модели\RevitModelLiteProcessorJournal.json`.
Путь закреплён регрессионным тестом; `G:` и альтернативные fallback-пути не используются.

Связь: [[Путь с кириллицей не открывался — виноваты бэкслеши, а не кодировка]] — тот же класс: путь ломается на экранировании, а сообщение об ошибке винит что-то другое.
