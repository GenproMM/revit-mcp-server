# Сессия: открытие без отсоединения создаёт локальную копию, RSN-путь больше не зависит от журнала

**Дата:** 2026-09-17  
**Модель:** Claude Opus 5 (1M context)  
**Изменено файлов:** 3  

## Суть работы

Запрос был проверить, создаётся ли локальная копия при открытии модели с Revit Server без отсоединения. Не создавалась — это реальный дефект, а не недоразумение.

При `detach="none"` маршрут передавал `ModelPath` **центральной модели** прямо в `OpenAndActivateDocument`. В Revit API нет автоматического создания локальной: галочка *Create New Local* в диалоге Open — это отдельный вызов `WorksharingUtils.CreateNewLocal`. Без него Revit открывал сам центральный файл. Для файловой центральной это классический путь к повреждению модели, центральную на Revit Server так открыть нельзя вообще.

Docstring инструмента при этом прямо обещала обратное поведение как задуманное: `"none" opens the central file itself without detaching`. То есть поведение было задокументировано, но неверно по существу.

По ходу сессии пользователь сообщил второй симптом с рабочих мест: агент отвечает «MCP-bridge не может открыть RSN:// путь напрямую, нужно открыть модель вручную». Этой строки в репозитории нет — её сочиняет агент, когда инструмент падает. Причин оказалось две, обе разобраны ниже.

## Изменённые файлы

- `revit_mcp/worksharing.py` — создание локальной копии, расширенный детект RSN
- `tools/worksharing_tools.py` — параметры `local_path`/`overwrite_local`, проброс полного RSN мимо журнала, расширенный детект RSN
- `tests/unit/test_revit_server_paths.py` — новый файл, разбор RSN-путей

## Что сделано

**Локальная копия.** При `detach="none"` на центральной модели (включая любую RSN) сначала создаётся локальная через `CreateNewLocal`, открывается именно она. Имя по конвенции самого Revit: `Documents/<Модель>_<пользователь>.rvt`. Ответ содержит `is_local_copy`, `local_path`, `replaced_existing_local`.

Две детали, которые легко пропустить:

- `CreateNewLocal` **отказывается** писать поверх существующего файла. Старая копия удаляется первой. Отсюда `overwrite_local=false` — защита от молчаливой потери несинхронизированной работы. Если копия открыта в Revit, удаление не пройдёт, и приходит внятная ошибка вместо загадочного отказа API.
- `BasicFileInfo.IsCentral` на части версий возвращает `None`, поэтому копия создаётся и при неизвестном флаге. Лишняя копия безвредна, открытая центральная — нет.

**Полный RSN больше не ходит в журнал.** `_resolve_revit_server_path` **всегда** обращался к `//srv-dfs/BIM/.../RevitModelLiteProcessorJournal.json`. Недоступная шара превращала корректный `RSN://сервер/папка/Модель.rvt` в ошибку до того, как запрос доходил до Revit. Теперь полный URI проходит насквозь; журнал нужен только для сокращения вида `RSN://Модель.rvt`. Текст ошибки для сокращения теперь называет журнал и предлагает передать полный путь.

## Что я открыл

Главная находка — **тест поймал баг, который я сам внёс и сначала неверно диагностировал**.

Проверка `startswith("rsn://")` не узнаёт написание `RSN:\\srv\Projects\Model.rvt`, которое пользователи копируют из Windows-диалогов. Такой путь уходил в ветку локальных файлов, где `os.path.exists()` объявлял модель отсутствующей — второй источник жалобы «не может открыть RSN».

Я сначала решил, что дело в порядке нормализации (сначала срезали схему, потом заменяли разделители). Это было неверно. Настоящая причина: после замены `\` → `/` строка `RSN:\\srv\...` даёт `RSN:/srv/...` с **одним** слешем, и префикс `rsn://` не совпадает. Количество разделителей после двоеточия зависит от того, как путь экранировали по дороге.

Итоговая проверка — `.replace("\\", "/").startswith("rsn:/")`, то есть один слеш как минимум, а разбор на сегменты идёт через `split(":", 1)`, а не через срез фиксированной длины. Исправлено **с обеих сторон моста**: два одноимённых `_is_revit_server_path` в `revit_mcp/` и `tools/` живут независимо, и расхождение между ними дало бы новый класс расхождений.

Побочное наблюдение по инструментам: вложенные heredoc'и в Bash съедают обратные слеши на каждом уровне. Три попытки написать тестовый литерал с `\\` через `python - <<'EOF'` дали три разных неверных результата. Файлы с обратными слешами надо писать инструментом Write, а не через heredoc.

## Что не готово

`CreateNewLocal` **не проверен на живом Revit** — юнит-тестами эта ветка не покрывается, она требует pyRevit. Покрыт тестами только разбор RSN-путей на стороне CPython.

План проверки:

1. Полный перезапуск Revit (не Reload — он крашит процесс, см. [[pyRevit Reload при включённых Routes валит Revit на первом же запросе]])
2. `Get-NetTCPConnection -LocalPort 48884 -State Listen` — убедиться, что слушатель один
3. `open_model` с `detach="none"` на реальной RSN-модели
4. Проверить, что в `Documents` появился `<Модель>_<пользователь>.rvt`
5. Проверить, что Synchronize with Central доступен — это и есть смысл всей правки

Отдельно не проверено поведение при уже открытой в Revit локальной копии: ветка написана и возвращает осмысленную ошибку, но живого прогона не было.
