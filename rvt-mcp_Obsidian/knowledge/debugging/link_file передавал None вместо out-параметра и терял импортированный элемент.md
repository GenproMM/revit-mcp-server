# link_file передавал None вместо out-параметра и терял импортированный элемент

**Статус:** исправлено · коммит `2d9002f`

## Симптом

`link_file` сообщал об успехе, но не возвращал идентификатор импортированного элемента.
Работать с только что вставленной геометрией было нечем — её нельзя было ни найти, ни
переместить, ни удалить через API.

## Причина

`doc.Import(...)` и `doc.Link(...)` в Revit API принимают **out-параметр** `ElementId`,
в который записывают результат. Обработчик передавал туда `None`, поэтому вызов
проходил, а идентификатор терялся.

В IronPython out-параметры .NET требуют явной обёртки — просто передать переменную
недостаточно.

## Исправление

Использование `clr.Reference` для out-параметра:

```python
import clr
out_id = clr.Reference[DB.ElementId]()
doc.Import(path, options, view, out_id)
element_id = get_element_id_value(out_id.Value)
```

Тем же коммитом расширен список форматов: к DWG / DXF / DGN / RVT добавлены **SAT, SKP,
3DM** — 3D-телесные форматы, нужные для импорта реальной геометрии высокой
достоверности. Соответственно появились `SATImportOptions` и `SKPImportOptions`.

## Урок

> Out-параметр .NET в IronPython — это `clr.Reference[T]()`, а не `None` и не обычная
> переменная. Вызов с `None` **не падает**, он просто теряет результат.

Класс проблем: вызовы Revit API, которые «работают», но чей полезный результат уходит
в никуда. Проверка простая — если сигнатура .NET-метода содержит `out`, то на стороне
IronPython обязан быть `clr.Reference`.

Заодно это ещё один пример правила из
[[Окна и двери без хоста прилипали к началу координат]]: успешный вызов Revit API не
означает осмысленного результата.
