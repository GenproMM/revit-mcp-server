# Фаза 4 — вторичный сбой даёт partial, outcome есть и в execute_code, и в ответах 500

**Контекст.** `04-CONTEXT.md` (D-01..D-11) задаёт блок `outcome` рядом со старыми ключами и чистую `classify_outcome` (409 `rolled_back` / 200 `success` / 200 `partial` / 422 `failed`). Исследование при планировании оставило открытыми вопросы, которые меняют контракт ответа — а его прочитает журнал аудита фазы 6 (D-03 помечен как costly). Пользователь ответил 2026-10-23.

**Решение пользователя (D-12..D-15).**
- **D-12.** Элемент создан, но вторичный шаг не удался (свойства `place_family`, размеры `create_duct`, стиль линии `detail`, имя `create_level`) → шаг идёт в `outcome.failed` с `item` = имя шага, созданный id — в `succeeded`, итог **200 `partial`**. Эти маршруты сознательно меняют `success` на `partial`.
- **D-13.** `/execute_code/` тоже несёт `outcome` (`requested: null`, пустые списки, реальный `transaction_status`) — одна схема для фазы 6.
- **D-14.** Ответ 500 любого маршрута с транзакцией несёт `outcome` с реальным статусом: исключение после `Commit()` показывает `Committed`, а не прячет изменение модели. `GetStatus()` — в `try/except`, при сбое `null`.
- **D-15.** `create_mep_system`: при `new_system is None` транзакция откатывается, ответ **422 `failed`** (раньше фиксировалась пустая транзакция и шёл 500).

**Решения планировщика по своему усмотрению (ждут подтверждения).**
- Ключа `item_kind` нет — схема D-03 зафиксирована.
- При 409 старые ключи из ответа убираются (они назвали бы несуществующие элементы), `outcome.succeeded == []`.
- D-12 распространён на похожие тихие пропуски: номер/имя листа, поля спецификации, имена сетки/уровня/вида/помещения, имя MEP-системы, поворот `place_family`.
- `edit_family` без единой удачной правки → 422 без перезагрузки семейства.
- `set_parameter` с неподдерживаемым типом → откат и 400 вместо ложного успеха.
- PDF-экспорт, вернувший False → 422 вместо 500.
- `/activate_document/` остаётся без `outcome` (это активация, не мутация модели); фаза 6 обрабатывает его явно по имени маршрута.

**Почему так.** Журнал аудита фазы 6 должен читать одну схему и не записывать ту же ложь, которую он призван разоблачить: созданный элемент с проваленным шагом, 500 после фиксации и пустой commit — именно такие «успехи».

**Как применять.** `partial` — **не** сигнал ошибки: множество `error/failed/failure/exception` в `format_response` не меняется (см. [[Провал ответа определяется только ключом error или явным статусом]]); 409 `rolled_back` остаётся несущим. Новый мутирующий маршрут фиксирует только через `commit_and_report` с сохранённым `swallower` — после плана 04-08 голый `.Commit()` отвергает `scripts/conventions.py`.
