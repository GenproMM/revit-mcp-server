model sees), how the new outcome statuses look: PARTIAL SUCCESS with the failed items, HTTP 422
`failed` when nothing succeeded, HTTP 409 `rolled_back` when Revit rolled the transaction back, and

in `tools/`; no behaviour change.

## The four paragraphs (paste verbatim, as its own paragraph immediately before `Args:`)

- **P (partial or total failure):** "Outcome: the reply reports what Revit actually did. If some items or
  follow-up steps (such as setting a name, a parameter or a line style) fail, the reply starts with
  PARTIAL SUCCESS and lists each failure with its reason; everything else was applied. If nothing
  succeeds the reply is an error (HTTP 422, status failed). If Revit rolls the transaction back the
  reply is an error (HTTP 409, rolled_back) and nothing was changed."
- **S (created element, follow-up steps can fail):** "Outcome: the reply reports what Revit actually
  did. If the element is created but a follow-up step (such as setting a name, a number, a dimension,
  a property, a schedule field, the rotation or a line style) fails, the reply starts with
  PARTIAL SUCCESS, the created element stays in the model, and each failed step is listed with its
  reason. If Revit rolls the transaction back the reply is an error (HTTP 409, rolled_back) and
  nothing was changed."
- **E (fails without partial):** "Outcome: if Revit reports that the operation did not happen (for
  example the export call returned False or no element id came back), the reply is an error
  (HTTP 422, status failed) with the reason. If Revit rolls the transaction back the reply is an error
  (HTTP 409, rolled_back) and nothing was changed."
- **A (all or nothing):** "Outcome: all or nothing. If Revit rolls the transaction back the reply is
  an error (HTTP 409, rolled_back) and nothing was changed."

Classification (mirrors 04-01..04-07; P 14 + S 7 + E 4 + A 3 + EXEMPT 3 = the 31 MUTATION_TOOLS):

## Scope note (file count): why 15 files in one plan is safe

This plan modifies 15 files (14 `tools/*_tools.py` plus one new test), above the usual split line,
and is deliberately kept as one plan rather than split:

- The change is text only. Each tool edit inserts one fixed paragraph (copied verbatim from above)
  into an existing docstring; no signature, import, body, return value or Args entry changes, and
  Task 1's acceptance criteria check that no code line moved.
- The 14 tool files total about 1,960 lines (largest `tools/family_tools.py`, 285 lines); the executor
  reads only the target functions' docstrings (locate each with `grep -n "async def <name>("`, then
  read from that line to its `Args:`), so the reading cost stays near 30k tokens for the whole plan.
- Each task touches at most five files and has its own AST check of required and forbidden phrases,
  so a slip is caught inside the task that made it.
- Splitting would add a plan and push the contract test, which checks the docstrings of both halves,
  into a later wave, with no reduction in risk.

## Execution rules for every task in this plan

- Edit docstrings only: no signature, default, Args entry or body change. Keep 8-space docstring
  indentation and wrap lines like the surrounding text, but never break a checked phrase across a
  line: "PARTIAL SUCCESS", "HTTP 422" and "HTTP 409" each stay whole on one docstring line, because
  the checks match the literal phrase.
- Commit protocol: `uv run pytest tests/unit -q` green before every commit; explicit pathspec commits
  only (`git commit -m "<message>" -- <paths>`; Task 3 first runs `git add -- tests/unit/test_outcome_docstrings.py`
  because a pathspec commit rejects an untracked file); never `git add -A`/`.`; the user's staged
  files stay staged. Prefix `docs(04-09):` / `test(04-09):`; end with your session's attribution line.
