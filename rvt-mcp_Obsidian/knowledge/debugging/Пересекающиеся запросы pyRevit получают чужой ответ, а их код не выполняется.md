# Пересекающиеся запросы pyRevit получают чужой ответ, а их код не выполняется

**Статус:** измерено на живом стенде (план 01-04, эксперимент D-23), воспроизводится два раза
из двух. Обход в нашем сервере запланирован (d27-b), исправление на стороне Revit отложено (d27-c).

## Симптом

Два запроса к одному Revit, пришедшие почти одновременно, оба отвечают `200`, но второй
получает **ответ первого**. Код второго запроса при этом не выполняется вовсе.

## Как измерено

`scripts/probe_handler_overlap.py --port 48884` шлёт сырые запросы мимо замка `bridge.py`:

- **Фаза M (изменение + изменение).** A: `/execute_code/` со сном 4 с; B: без сна через 0,5 с.
  Итог: `B got=MARK-A-...`, `RUNS A=1 B=0` — B ответил «успешно», но не выполнился.
- **Фаза R (изменение + чтение).** C: `/execute_code/` со сном; через 0,5 с `GET /list_levels/`
  и `GET /status/`. Итог: `list_levels` вернул `MARK-C-...` вместо уровней. `/status/` ответил
  за 0,01–0,02 с без подмены.

## Причина

В pyRevit 6.5.3 один общий обработчик запросов (`REQUEST_HNDLR`/`EVENT_HNDLR` в `server.py`)
на все HTTP-потоки, без лока. Все ждущие вызывающие получают результат того запроса, который
сейчас исполняется. `/status/` (и, по чтению исходников, `/model_info/`) выполняются прямо на
HTTP-потоке и сюда не попадают. `/model_info/` не измерен.

## Чем опасно

- Изменение может молча потеряться при ответе «успешно».
- Чтение может вернуть чужие данные.
- Замок `bridge.py` действует внутри одного процесса сервера. Каждый сеанс ассистента — свой
  процесс, поэтому два сеанса с одним Revit не защищены ничем.
- Allowlist чтений мимо замка (D-08) в текущем виде небезопасен.
