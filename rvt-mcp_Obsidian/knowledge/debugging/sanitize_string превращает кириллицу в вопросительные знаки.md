# sanitize_string превращает кириллицу в вопросительные знаки

**Статус:** исправлено · найдено на живой русскоязычной модели

> [!success] Обновление той же датой, другая сессия
> В первой сессии, где найден этот баг, пользователь запретил трогать код
> репозитория — правка описана ниже только как рекомендация. В следующей,
> независимой сессии (без памяти о первой) баг был найден заново тем же путём,
> и на этот раз пользователь явно попросил исправить. Правка внесена — ровно
> вариант 1 из раздела «Варианты» ниже, плюс найдена **вторая, независимая**
> копия того же ASCII-фильтра в `revit_mcp/parameters.py` (`_safe_str`,
> посимвольный `ord(ch) >= 128 → '?'`), которую первая сессия не нашла — она
> искала только `encode('ascii', ...)` и эту вариацию не поймала. Обе копии
> исправлены. Подробности: [[2026-09-04 — фикс кириллицы и правильный детект общих параметров, новый инструмент list_project_parameters]].

## Симптом

Любое имя элемента с кириллицей — уровня, стены, семейства, категории, параметра —
приходит в JSON-ответе как строка из `?`:

```
RAW (в самом Revit)     Уровень 1
SANITIZED (в ответе)    ??????? 1
```

Практическое следствие сильнее эстетического: `get_element_properties` вернул 49
параметров стены, но ни один параметр с русским именем нельзя было опознать —
«Площадь» неотличима от «Периметра», обе стали `???????`. Пришлось обходить штатный
инструмент и запрашивать `BuiltInParameter.HOST_AREA_COMPUTED` напрямую через
`execute_code`.

`document_title` в ответе `/status/`, напротив, приходит читаемым
(`"Проверка_ОТверстий"` корректными `\uXXXX`-эскейпами) — потому что берёт `doc.Title`
напрямую, минуя проблемную функцию. Эта асимметрия — первая улика.

## Причина

`revit_mcp/utils.py`, функции `sanitize_string` (строки 59-66) и `normalize_string`
(строка ~54):

```python
def sanitize_string(text):
    """Sanitize a string to be ASCII-safe for JSON serialization."""
    return str(text).encode('ascii', 'replace').decode('ascii')
```

`get_element_name()` вызывает `sanitize_string()`, и через неё проходят **19 из 23**
модулей маршрутов — отсюда массовый эффект.

Это **регрессия форка**, не апстрима. В апстримном
`mcp-servers-for-revit/mcp-server-for-revit-python` та же функция выглядит так:

```python
def get_element_name(element):
    try:
        return element.Name          # .NET string, юникод не трогается
    except AttributeError:
        return DB.Element.Name.__get__(element)
```

`git log -S sanitize_string` в этом репозитории указывает на коммит `bb7cda2`
(«Add multi-version Revit support (2024/2025/2026)», Talal Ahmed) — ASCII-энкодинг
приехал попутным грузом в коммите, который по названию и содержанию занимался
централизацией версионных различий `ElementId`, про кодировки в сообщении ни слова.

## Доказательство, что фикс не нужен по существу

Прямой эксперимент на живой модели через `execute_code`: прочитать `.Name` сырым и
рядом применить форковое преобразование к тем же уровням.

```
RAW=Уровень 1          |  SANITIZED=??????? 1
RAW=Фунд. стена T.O.   |  SANITIZED=????. ????? T.O.
RAW=Основание B.O.     |  SANITIZED=????????? B.O.
```

Сырое имя доезжает целым — JSON-сериализатор pyRevit прекрасно эскейпит юникод в
`\uXXXX`. Докстринг «ASCII-safe for JSON serialization» не соответствует
действительности: сериализация не требует ASCII, это выдумка функции.

## Почему не было исправлено сразу

В первой сессии, где найден баг, пользователь прямо попросил не редактировать код
репозитория — «должно работать из коробки», без правок. Настройками эта проблема не
лечится, она в коде. Во второй сессии этот запрет снят пользователем явно.

## Как в итоге исправлено

Вариант 1 ниже — применён буквально. `sanitize_string`/`normalize_string` в
`revit_mcp/utils.py` теперь сохраняют unicode как есть, гвардируя только `None` и
неожиданные типы. Проверено на живой модели после полного перезапуска Revit:
`view_name` = «План 1-го этажа» вместо `??? 1-?? ?????`.

## Варианты (исторический список на момент первой сессии)

1. **Выполнено.** Вернуть `sanitize_string`/`normalize_string` к апстримному
   поведению — две строки в одном файле. Junction на расширение уже настроен,
   подхватится перезапуском Revit.
2. Завести issue апстриму форка (Demolinator) — не сделано, остаётся открытым
   вопросом.
3. Откатиться на апстримное расширение через pyRevit Extensions — но тогда теряются
   добавки форка: поддержка 2027, clash-детект, `save_document`, `load_family` и
   часть из 48 инструментов. Отклонено ещё в первой сессии.

## Урок

> Докстринг, объясняющий *зачем* сделано преобразование, может быть просто неверным.
> Не верить на слово — воспроизвести оба пути (сырой и «санитизированный») рядом на
> одних и тех же данных, это заняло один вызов `execute_code`.

Также: если правка приехала в коммите с несвязанным названием — искать точечно
через `git log -S <строка>`, а не читать сообщение коммита.
