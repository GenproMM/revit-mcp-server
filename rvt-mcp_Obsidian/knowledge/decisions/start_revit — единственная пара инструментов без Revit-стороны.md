# start_revit — единственная пара инструментов без Revit-стороны

Пользователь потребовал: «MCP server должен уметь открывать Revit» — до этого
момента 49 из 49 инструментов предполагали, что Revit уже открыт и pyRevit
Routes уже отвечает.

## Решение

Новый модуль `tools/process_tools.py`, два инструмента:
- `get_revit_process_status` — какие версии Revit установлены, отвечает ли мост,
  открыт ли документ. Безопасен всегда — ничего не запускает и не меняет.
- `start_revit` — находит `Revit.exe` под `C:\Program Files\Autodesk\Revit *`
  (переопределяется `REVIT_EXE`), запускает detached с stdio на `DEVNULL`
  (унаследованный stdout испортил бы протокол MCP), поллит мост до готовности
  или `wait_seconds` (по умолчанию 240с).

Это единственная пара инструментов, у которой **нет зеркальной Revit-стороны**
в `revit_mcp/` — нарушение правила «правка через 4 места» из CLAUDE.md
осознанное: делать зеркало некому, пока Revit не запущен.

## Особенности реализации

- `ctx.info()` бросает исключение вне активного request-контекста — обёрнуто
  в `_say()`, best-effort, никогда не роняет вызов. Долгий инструмент (запуск
  Revit — 60-180с) не должен падать из-за потери строки прогресса.
- Мост проверяется трёхзначно, не булево — см.
  [[get_revit_process_status различает Revit закрыт от Revit без документа]].
- В managed-блок Hermes (`deploy/configure_hermes.py`) добавлен
  `timeout: 600` — дефолтный таймаут клиента иначе оборвёт вызов на прогреве
  холодного Revit.

## Не проверено вживую

Зелёный путь «Revit поднялся → мост ответил» не пронаблюдан целиком: в тесте
Revit 2027 стартовал (PID подтверждён), но завершился раньше, чем поднялся
Routes — причина не выяснена. Логика покрыта 22 детерминированными тестами
с подставным мостом, но не единым сквозным прогоном на реальном Revit.
Стоит проверить на пилотной станции.
