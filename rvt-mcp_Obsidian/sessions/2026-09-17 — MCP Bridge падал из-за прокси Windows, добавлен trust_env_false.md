# Сессия: MCP Bridge падал из-за прокси Windows

**Дата:** 2026-09-17
**Модель:** gpt-5.6-luna (gp_gpt)
**Исходная сессия:** `20260916_183650_b056c2` — `/gsd-autonomous — phase v260911 REQ-205001…`

## Суть работы

Разобрана проблема, при которой MCP Bridge возвращал пустое `Error: ` при вызове инструментов Revit.

## Диагностика

- `hermes mcp test revit`: подключение успешно, обнаружено 54 инструмента.
- pyRevit Routes на `127.0.0.1:48884` отвечает HTTP 200.
- Нативный `http.client` получает корректный ответ.
- `httpx.AsyncClient` с настройками окружения получает `ReadError('')`.
- Тот же `httpx` с `trust_env=False` получает HTTP 200.

Корневая причина: MCP subprocess наследовал настройки Windows-прокси, и `httpx` применял их к локальному адресу `127.0.0.1`. pyRevit Routes разрывал соединение, а пустой текст `ReadError` превращался в неинформативное `Error: `.

Отдельно установлено: отсутствие слушателя на порту 8000 не является ошибкой — сервер подключён к Hermes через stdio; порт 8000 нужен только для HTTP-транспорта MCP.

## Изменения

- `main.py`: для локального `httpx.AsyncClient` добавлен `trust_env=False`.
- `tests/unit/test_local_bridge_transport.py`: добавлен регрессионный тест.
- Локальный payload обновлён в `%LOCALAPPDATA%\\RevitMCP\\current\\app\\main.py`.
- В Obsidian добавлены эта запись, ссылка в `00-home/index.md` и запись в `00-home/текущие приоритеты.md`.

## Проверки

- Полный unit-набор: **338 passed, 3 skipped**.
- `hermes mcp test revit`: **Connected**, обнаружено 54 инструмента.
- Прямой MCP-вызов `get_selected_elements`: успешен, вернул `1 element currently selected`.
- После остановки старого MCP-процесса повторный вызов ожидаемо дал `All connection attempts failed`; для запуска нового процесса нужен перезапуск Gena Desktop.
