## The outcome contract (defined here, imported by every later plan)

All five helpers live in `revit_mcp/textutils.py` (pure: imports nothing from pyRevit, so CPython
tests import it directly; written at the Python 3.4 language level because the Revit half runs it
under IronPython 3). A new helper module was rejected because `tests/unit/test_registration.py` and
`scripts/conventions.py` hard-code the helper set (RESEARCH "Alternatives Considered").

- `classify_outcome(committed, n_succeeded, n_failed)` returns `(status, http_status)`:
  not committed gives `("rolled_back", 409)`; committed with `n_failed == 0` gives `("success", 200)`;
  committed with both counts above zero gives `("partial", 200)`; committed with `n_succeeded == 0`
  and `n_failed > 0` gives `("failed", 422)`.
- `build_outcome(transaction_status, requested, succeeded, failed, revit_failures)` returns a dict with
  exactly the five D-03 keys `transaction_status`, `requested`, `succeeded`, `failed`,
  `revit_failures`. Lists are new lists in the given order (no sort, no dedupe). Each failed entry is
  reduced to `{"item": entry["item"], "reason": sanitize_value(entry.get("reason"))}`: any other key a
  route attached is dropped, so nothing else (secret, body, traceback) can ride along.
- `finalize_outcome(commit_result, data, requested, succeeded, failed)` returns `(payload,
  http_status)`; `commit_result` is the dict `commit_and_report` returns; `data` is never mutated.
  On 409 the payload is exactly `status` "rolled_back", `message` (fixed text: "Revit rolled the
  transaction back at Commit() (transaction_status: {status}); no change from this call was kept in
  the model. 'failures' lists what Revit reported."), top-level `transaction_status` and `failures`
  (the existing 409 contract), and `outcome` with `succeeded` [] and the route's `failed` list; the
  legacy keys of `data` are left out because they would name elements that no longer exist. On
  200/422 the payload is a copy of `data` with `status` set (overwriting any status in data) and
  `outcome` added; on 422 also `error` = "None of the {n} requested item(s) succeeded; each item and
  its reason is in outcome.failed" with n = requested, or len(failed) when requested is None.
- `transaction_status_of(transaction)` returns None for None, else `str(transaction.GetStatus())`
  inside `try/except Exception` returning None on any failure (assumption A2: GetStatus after Commit
  is readable; if not, null is honest).
- `exception_outcome(transaction, requested=None, succeeded=None, failed=None)` returns
  `build_outcome(status, requested, kept, failed or [], [])` where `status =
  transaction_status_of(transaction)` and `kept` is `list(succeeded or [])` only when status ==
  "Committed", else []. Used in every 500 (or colors' 200 "error") reply of a transacting route (D-14).

`commit_and_report` in `revit_mcp/utils.py` stays byte-for-byte unchanged.

### Route pattern every migration follows (later plans copy it)

1. Before the outer `try`: `t = None`, `requested = None`, `succeeded = []`, `failed = []`.
2. Validation that refuses before any transaction (400/404/503) stays exactly as it is and carries no
   outcome (D-04). An in-transaction validation branch that calls `t.RollBack()` and answers 4xx also
   stays as it is.
3. `t = DB.Transaction(...)`, `t.Start()`, then on the very next line `swallower = suppress_warnings(t)`.
4. Per item: on success append the item handle to `succeeded`; where the route today appends to
   `skipped`/`errors` or logs and `continue`s, also append `{"item": handle, "reason": text}` to
   `failed`, with text = the route's existing reason string or `str(exc)`.
5. `commit_result = commit_and_report(t, swallower)`, then `payload, http = finalize_outcome(
   commit_result, data, requested, succeeded, failed)` and `return routes.make_response(data=payload,
   status=http)`. Any read of element state that today happens after the commit moves after a check of
   `commit_result["committed"]` (on not-committed return the 409 at once).
6. The outer `except Exception as e` reply keeps its keys and gains `"outcome": exception_outcome(t,
   requested, succeeded, failed)`; the traceback stays where it is today (HYG-01 deferred), never in
   outcome.

### Item convention (Claude's discretion, recorded in CONTEXT; applies to every plan)

| Route kind | `succeeded` entries | `failed[].item` |
|---|---|---|
| acts on existing elements by id (tag_elements, tag_walls, delete_elements, transform_elements, color_splash, clear_colors) | the input element id | the input element id |
| parameter writers (modify_element, set_parameter, edit_family) | parameter name | parameter name (edit_family also "shared:NAME", "new_type:NAME") |
| batch creation (create_line, create_surface, create_level, create_grid, create_framing, create_room_separation) | id of the element created | 0-based input index (int) when nothing was created; "INDEX.STEP" string (e.g. "0.name") for a failed secondary step of a created item (D-12) |
| single-element creation (create_dimensions, create_detail_line, create_duct, create_pipe, create_mep_system, create_room, create_sheet, create_schedule, create_view, place_family) | id of the element created | step name (D-12: "line_style", "diameter", "width", "height", "system_name", "name", "number", "rotation", property or field name); create_dimensions: input element id whose reference could not be read, "dimension" when none was created; create_mep_system D-15: "system" |
| file I/O (export_ifc, export_document, link_file) | output or input file path | the same path |
| no transaction (save_document, open_model, set_active_view, load_family) | saved path or title, requested file path, view name, family file path | the same handle |
| execute_code | [] with requested null (D-13) | [] |

`requested` = number of items the route attempts: input list length for batches, 1 for single-element
and file routes, number of parameters for parameter writers, null for execute_code. A no-op (a wall
already tagged, a shared parameter already present) is in neither list and not counted (Pitfall 7).

## Flagged assumptions (spec-less edge probe, not silently dropped)

- TRUTH-04 (unclassified edge, unresolved): a client that looks only at HTTP codes cannot tell 200
  `partial` from 200 `success`. Accepted because D-04 fixes `partial` at 200 and the bridge turns only
  non-200 into error strings; the discriminators are `status` and the PARTIAL banner.
- A1: Revit never returns `Pending`/`Error` from `Commit()` here because `suppress_warnings` disables
  forced modal handling; if it does, the reply is 409 `rolled_back` with the verbatim status.

- `revit_mcp/` is IronPython 3 at the Python 3.4 language level: no f-strings, no `{**a}` or `[*a]`
  unpacking in literals (build dicts with `dict(a)` then `.update(b)`), no keyword-only arguments, no
  `async`, no `pathlib`, no annotations; encoding cookie stays on line 1; package siblings are
  imported relatively (`from .utils import ...`); never import one `revit_mcp/` domain from another.

  success path fail for a fake-only reason, arm the fake so the success path is real. Do not widen

  same commit as the module change (Pitfall 3).
