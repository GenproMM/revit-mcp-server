# Ошибки не выбрасываются, а возвращаются строками

## Решение

`_revit_call` в `main.py` глотает **каждое** исключение и возвращает строку:

```python
return response.json() if response.status_code == 200 else f"Error: {response.status_code} - {response.text}"
except Exception as e:
    return f"Error: {e}"
```

Модуль инструмента никогда не увидит исключения от транспорта.

## Обоснование

MCP-инструмент обязан вернуть текст клиенту. Пробросить исключение сквозь FastMCP
означает отдать модели непрозрачную ошибку протокола вместо диагностируемого
сообщения. Строка «Error: 503 - No active Revit document» полезнее для ИИ-клиента, чем
трейс `httpx.ConnectError`.

На Revit-стороне действует симметричное правило: обработчик маршрута никогда не
выбрасывает наружу, вся его тушка обёрнута в `try/except` с
`routes.make_response(data={"error": ...}, status=5xx)`.

## Цена решения

Тип результата вызова моста молча меняется с `dict` на `str`. Вызывающий обязан
обрабатывать оба варианта, и единственное, что спасает вывод от мусора, —
`format_response`.

> [!warning] Никогда не индексировать результат моста напрямую
> `result["clashes"]` упадёт с `TypeError`, когда мост вернул строку ошибки. Всегда
> прогоняйте результат через `format_response`.

## Как это применять

Тело инструмента всегда заканчивается одинаково:

```python
response = await revit_post("/clash_check/", data, ctx)
return format_response(response)
```

Тип возврата инструмента — всегда `-> str`.

## Что ещё не сделано

Ошибки инструментов уходят клиенту, но **не логируются** на MCP-стороне. Плюс нет
корреляционного идентификатора, связывающего вызов инструмента с породившим его
запросом Routes. Диагностика зависшей операции через границу процессов сейчас
невозможна.
