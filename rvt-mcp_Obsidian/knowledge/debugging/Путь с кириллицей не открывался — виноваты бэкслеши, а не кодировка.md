# Путь с кириллицей не открывался — виноваты бэкслеши, а не кодировка

**Статус:** исправлено · найдено по жалобе пользователя на живом пути с Google Диска

## Симптом

`open_model` не открывает файл с кириллическим путём:

```
G:\общие диски\10_bim_lab\4_plugins\0_сводныйреестрплагинов\02_тестирование\206_оформление зон армирования\nak_rd_1_st_кж2.3_отсоединено.rvt
```

Ответ — `404 Model not found: <путь>`, причём путь в сообщении выглядит
**почти правильно**. Файл при этом на диске есть и читается.

Формулировка жалобы — «MCP не может открыть файл с кириллическим путём» — и
есть главная ловушка этого бага: кириллица тут ни при чём.

## Причина — коллизия бэкслеша, а не юникод

Путь Windows, попавший в **неэкранированный строковый литерал**, теряет каждый
бэкслеш, образующий валидную escape-последовательность:

| В пути         | Во что превращается          |
|----------------|------------------------------|
| `\10_bim_lab`  | `\x08` (backspace) + `0_bim_lab` |
| `\4_plugins`   | `\x04` + `_plugins`          |
| `\0_сводный…`  | `\x00` (NUL)                 |
| `\02_тест…`    | `\x02` + `2_тест…`           |
| `\nak_rd…`     | перевод строки + `ak_rd…`    |

Кириллица **маскирует** проблему: `\о` — не валидный escape, поэтому такие
сегменты доезжают целыми, а `\10` молча становится управляющим символом. Путь
в сообщении об ошибке выглядит правдоподобно, и подозрение падает на кодировку.

## Доказательство, что кодировка ни при чём

Проверено по всей цепочке, независимо от Revit:

1. `json.dumps` в `main.py` эскейпит не-ASCII в `\uXXXX` — **на проводе только
   ASCII-байты**. Проверено: `all(b < 128 for b in body)` → `True`.
2. `parse_request_data` (`revit_mcp/textutils.py`) восстанавливает строку
   посимвольно точно — roundtrip на настоящем пути пользователя даёт `True`.
3. Корректно экранированный путь **существует на диске**: `os.path.isfile` →
   `True`, размер 65 609 728 байт, все сегменты проходятся по одному.

Решающая проверка — мимо Python вообще, на голом .NET (тот же слой, что зовёт
IronPython изнутри Revit):

```
File.Exists                              -> False
IndexOfAny(Path.GetInvalidPathChars())   -> 18
```

Символ на позиции 18 — `U+0008`. Ни один легальный путь Windows не может
содержать управляющий символ, так что это однозначная улика.

## Как исправлено

Добавлен `describe_broken_path()` — детектор, а не «чинилка»: находит
управляющие символы и объясняет **настоящую** причину вместо голого
«не найдено». Восстановить путь нельзя — информация уничтожена до прихода в MCP.

Функция **продублирована** в двух местах по [[Правило двух рантаймов]]:
`revit_mcp/textutils.py` (IronPython) и `tools/utils.py` (CPython) — половины
репозитория не делят интерпретатор и не могут импортировать друг друга.
Отдельный тест сверяет, что копии не разошлись.

Подключена во всех точках, принимающих путь: `open_model`,
`list_model_worksets`, `start_revit`, `save_document`, `load_family`,
`export_ifc`, `link_file` и оба 404 на стороне Revit. На стороне CPython
проверка стоит **до** обращения к мосту — незачем тратить round-trip на
заведомо мёртвый путь.

В докстринги инструментов добавлено правило экранирования: докстринг читает
модель, и это дешевле, чем ловить ошибку постфактум
(см. [[Докстринг инструмента — это контракт для модели, а не для разработчика]]).

## Рабочие формы пути

Все три открывают файл:

```
"G:\\общие диски\\10_bim_lab\\...\\nak_rd_1_st_кж2.3_отсоединено.rvt"   удвоенные
r"G:\общие диски\10_bim_lab\...\nak_rd_1_st_кж2.3_отсоединено.rvt"      raw-строка
"G:/общие диски/10_bim_lab/.../nak_rd_1_st_кж2.3_отсоединено.rvt"       прямые слеши
```

## Тот же класс бага уже кусал нас в инструментах

В сессии 2026-09-11 heredoc в Bash съедал бэкслеши по дороге в Python, и пути
`\\srv-dfs\BIM\06_RevitMCP` приезжали битыми в Wiki и `USER-GUIDE.md`. Тогда
это сочли особенностью работы с инструментами. Теперь ясно, что это **один и
тот же дефект**, и он бьёт по продукту, а не только по нашему тулингу.

Ирония: та же ловушка сработала **трижды при написании самого фикса** —
heredoc последовательно съедал бэкслеши в `_ESCAPE_CULPRITS`, в примерах
внутри текста ошибки и в тестовом файле. Лечится только сборкой через `chr(92)`
и плейсхолдеры, с обязательной проверкой готового файла.

## Урок

> Формулировка симптома пользователем — это гипотеза, а не диагноз. «Не
> работает кириллица» звучало как проблема кодировки, а оказалось escape-
> последовательностями; кириллица лишь сделала поломку незаметной.

Практический приём: проверять цепочку **по слоям и снаружи языка**. Голый
`File.Exists` на .NET дал однозначный ответ за один вызов, тогда как рассуждения
про UTF-8 внутри Python вели в сторону.

Второй урок: управляющий символ в пути — идеальный детектор, потому что
**не бывает ложноположительных**. Windows не разрешает такие символы в именах.
