# Докстринг инструмента — это контракт для модели, а не для разработчика

## Почему это буквально так

FastMCP генерирует схему инструмента из тайп-хинтов и **докстринга** через pydantic.
Отдельного описания API не существует — то, что написано в докстринге, и есть всё, что
языковая модель знает об инструменте перед вызовом.

Значит докстринг пишется **для модели**: не «что делает функция», а «когда это
вызывать, с чем, и что вернётся».

## Эталон — `check_clashes` в `tools/clash_tools.py`

```python
"""Detect hard clashes (geometric interferences) between model elements.

Runs Revit's native interference logic to find elements whose solids
physically overlap — the core of BIM coordination (e.g. ducts running
through beams, pipes through walls).

Scope rules:
  - No categories given: a default physical scope (architectural +
    structural + MEP) is checked against itself.
  - Only set_a given: set_a is checked against itself.
  - Both given: set_a is checked against set_b (cross-discipline),
    e.g. structure vs MEP.

Categories accept BuiltInCategory ids ("OST_DuctCurves") or friendly
aliases ("ducts", "pipes", "beams", "walls", "structural framing").

Returns clashing element pairs with ids, names, categories, and the
approximate clash location in mm. Note: auto-joined concrete and
geometry-less elements (e.g. rebar) are not reported by Revit.

Args:
    set_a_categories: First element set, e.g. ["beams", "OST_StructuralColumns"]
    set_b_categories: Second element set to check against, e.g. ["ducts", "pipes"]
    max_clashes: Maximum clashes to return (defaults to 200)
    ctx: MCP context for logging
"""
```

## Структура, которую он задаёт

1. **Одна строка назначения** — что это и зачем, с примером из предметной области.
2. **Правила поведения / области действия** — как ведёт себя инструмент при разных
   комбинациях входа. Это самая ценная часть: она снимает необходимость угадывать.
3. **Формат допустимых значений** — с конкретными примерами строк.
4. **Форма возврата** — что именно придёт.
5. **Известные ограничения** — прямо в докстринге, не в отдельном документе.
6. **Блок `Args:`** — каждый параметр, **включая `ctx`**.

## Правила

- Примеры значений — обязательны. `["beams", "OST_StructuralColumns"]` работает,
  «список категорий» — нет.
- Ограничения указываются явно. Модель не может узнать, что Revit не сообщает о
  коллизиях самосоединяющегося бетона, никак иначе — и без этого будет считать пустой
  результат подтверждением отсутствия коллизий.
- Единицы указываются всегда: «location in mm».
- Дефолты дублируются словами: «defaults to 200».
- `ctx` описывается тоже — он попадает в схему.

## Docstring — часть исправления бага

Когда меняется поведение, докстринг меняется вместе с кодом, а не потом. Так было в
[[Балки садились на Z=0 вместо отметки уровня]]: описание инструмента обновлено в том
же коммите, потому что поведение, не совпадающее с описанием, приводит к неверным
вызовам — модель читает докстринг и верит ему.

## На Revit-стороне тоже

Докстринг обязателен у каждого модуля и каждого обработчика маршрута, но там аудитория
другая — разработчик. Там нужен ожидаемый payload:

```python
"""
Save the active document. If a file_path is given (or the document has
never been saved, e.g. it was started from a template), performs SaveAs;
otherwise saves in place.

Payload (all optional):
{
    "file_path": "C:\\path\\to\\Model.rvt",
    "overwrite": true
}
"""
```
