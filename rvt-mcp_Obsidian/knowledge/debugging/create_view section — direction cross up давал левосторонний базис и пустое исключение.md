# create_view section — direction cross up давал левосторонний базис и пустое исключение

**Статус:** исправлено · найдено при первом реальном прогоне сценария
«создать секцию» на живой модели — маршрут никогда не мог создать ни одну
секцию, ни при каком входном payload

## Симптом

`POST /create_view/` с `view_type: "section"` всегда падал одинаково:

```json
{"error": "", "traceback": "...\n    raise tx_error\nException\n"}
```

Пустая строка в `error` — Revit API вернул `ArgumentException` вообще без
сообщения. Маршрут для плоских видов и расписаний (`floor_plan`,
`OST_Walls`-schedule) работал в той же сессии тем же способом — баг был
специфичен именно для секций.

## Причина

`revit_mcp/view_management.py` строил базис секции так:

```python
right_vec = dir_vec.CrossProduct(up_vec).Normalize()
transform.BasisX = right_vec
transform.BasisY = up_vec
transform.BasisZ = dir_vec
```

Revit принимает `BoundingBoxXYZ.Transform` для секции только если он
**правосторонний**: `BasisX == BasisY.CrossProduct(BasisZ)`. Здесь
`BasisX = dir × up`, то есть `BasisZ × BasisY` — это в точности отрицание
правильного произведения. Определитель такого базиса равен **−1 для любой
пары перпендикулярных `direction`/`up`**, не только для конкретных значений
payload по умолчанию — то есть путь был сломан начиная с самого первого
коммита этой ветки кода, никаким входом это было не обойти.

Подтверждено арифметически (без Revit): для `direction=(0,1,0)`,
`up=(0,0,1)` — `up × direction` даёт определитель `+1`, `direction × up`
даёт `−1` при тех же `up`/`direction`. Тест на этом факте не требует Revit
вообще — только векторную алгебру.

## Диагностика

Причина не была видна из самого сообщения (пустая строка) — пришлось читать
исходники Revit API на предмет требований к `BoundingBoxXYZ.Transform` и
сверять порядок операндов вручную. Ключевой сигнал — что ошибка **не
зависела от input**: секция не создавалась вообще ни разу, значит баг не в
данных, а в самой формуле.

## Исправление

```python
right_vec = up_vec.CrossProduct(dir_vec)
if right_vec.GetLength() < 1e-9:
    # direction и up коллинеарны — иначе Normalize() упал бы глубоко в Revit API
    return 400, "section_box direction and up are parallel"
right_vec = right_vec.Normalize()
```

Порядок операндов развёрнут (`up × direction` вместо `direction × up`), плюс
добавлена явная проверка на параллельность `direction`/`up` **до**
`Normalize()` — раньше нулевой вектор ушёл бы в Revit API и там бы упал с
таким же неинформативным исключением.

`tests/unit/test_section_basis.py` — 7 тестов на самом исходном тексте
маршрута (файл `revit_mcp/view_management.py` не импортируется под CPython,
поэтому проверяется его код как текст, а не поведение): что используется
`up_vec.CrossProduct(dir_vec)`, что **не** используется обратный порядок, и
что параллельный случай отбивается до `Normalize()`. Отдельно —
параметризованный тест на голой векторной алгебре, доказывающий сам факт
(«up × direction» даёт +1, «direction × up» даёт −1) независимо от кода
маршрута — своего рода спецификация, зафиксированная как тест.

## Урок

> Пустое сообщение исключения — не повод считать баг непроверяемым.
> Геометрический инвариант (здесь — «правосторонность базиса») можно
> зафиксировать тестом на чистой арифметике, без Revit, и тем же тестом
> навсегда закрыть класс регрессии, а не единичный случай.
