# Как сделать свой инструмент для RevitMCP

Инструкция для тех, кто хочет добавить в RevitMCP новый инструмент, не имея
доступа к репозиторию сервера. Читайте по порядку, ничего не пропуская.

Коротко: вы соберёте один файл-архив на своём компьютере и положите его в
папку на сервере компании. Дальше его добавит в репозиторий сопровождающий.
Git и доступ к репозиторию вам не понадобятся.

---

## 1. Общая картина

RevitMCP состоит из двух частей, которые разговаривают между собой по сети:

- **часть внутри Revit** — принимает команды и работает с моделью;
- **часть снаружи** — с ней разговаривает ИИ-помощник (Hermes).

Ваш инструмент — это **ровно по одному файлу в каждую часть**. Больше ничего.
Именно поэтому его можно передать одним архивом, не трогая репозиторий сервера
и не давая вам к нему доступ.

Пример: инструмент «сводка стен по типам».

- Файл внутри Revit собирает стены и считает площади.
- Файл снаружи описывает модели, **когда** этот инструмент вызывать и что он
  вернёт.

Второй файл важнее, чем кажется. Языковая модель видит только его описание —
больше у неё ничего нет. Плохое описание означает, что инструмент будут
вызывать неправильно или не вызовут вовсе.

### Почему нельзя просто прислать код в общий файл

Три причины, и все технические, а не бюрократические:

1. **Атомарность.** Станции сотрудников грузят расширение из общей папки на
   сервере целиком. Если бы правки лились прямо в неё, кто-то мог бы открыть
   Revit ровно в момент, когда файлы наполовину обновлены — часть новая, часть
   старая. Публикация пересобирает папку расширения целиком за один раз, поэтому
   до этого момента все видят консистентную предыдущую версию.
2. **Пространство импорта.** Вся папка расширения попадает в путь поиска
   модулей IronPython. Лишний файл там — это лишнее место, откуда может
   случайно подгрузиться что-то неожиданное.
3. **Обзор кода — обязательный шаг.** Ваш код будет исполняться **внутри
   процесса Revit**, с полным доступом к API и файловой системе, на каждой
   станции отдела. Автоматика (см. главу 6) ловит нарушения правил и явно
   опасные конструкции, но не может оценить замысел. Поэтому пакет всегда
   читает и одобряет человек.

## 2. Настройка среды (один раз)

### 2.1. Проверьте, что Revit и RevitMCP работают

Откройте Revit и **откройте любую модель** — не пустое окно, именно модель.
Затем откройте в браузере:

```
http://localhost:48884/revit_mcp/status/
```

Ожидаемый результат: страница с текстом, где встречается `"health": "healthy"`.

| Что видите | Что делать |
|---|---|
| Не удаётся подключиться | Revit закрыт, или в нём не открыта модель. Откройте модель. |
| Страница пустая, но соединение есть | Расширение RevitMCP не загрузилось. Перезапустите Revit **полностью** — закрыть и открыть, не кнопкой Reload. |
| Не помогло | Напишите сопровождающему: без работающего моста делать инструмент нельзя. |

Без этого шага дальше нет смысла идти — вы не сможете проверить свою работу.

### 2.2. Найдите Python

Отдельно ставить ничего не нужно — Python уже приехал вместе с pyRevit.

Откройте Проводник и вставьте в адресную строку:

```
%APPDATA%\pyRevit\bin
```

Зайдите в папку `cengines`, там будет папка вида `CPY3123` (цифры могут
отличаться). Внутри — `python.exe`. Запомните полный путь к нему:

```
C:\Users\ВашеИмя\AppData\Roaming\pyRevit\bin\cengines\CPY3123\python.exe
```

Проверьте в PowerShell, подставив свой путь:

```powershell
& "C:\Users\ВашеИмя\AppData\Roaming\pyRevit\bin\cengines\CPY3123\python.exe" --version
```

Должно напечатать что-то вроде `Python 3.12.3`.

> Если у вас уже установлен свой Python 3 и команда `python --version`
> работает — используйте его, разницы нет. Набор работает на любом Python 3,
> без сторонних библиотек.

Совет, чтобы не писать длинный путь каждый раз — один раз в PowerShell:

```powershell
Set-Alias python "C:\Users\ВашеИмя\AppData\Roaming\pyRevit\bin\cengines\CPY3123\python.exe"
```

Действует до закрытия окна. Дальше в инструкции пишется просто `python`.

### 2.3. Распакуйте набор разработчика

Возьмите `revitmcp-contrib-kit.zip` из папки:

```
\\srv-dfs\BIM\01_Ресурсы плагинов\827_RevitMCP\contrib-kit\
```

Распакуйте **целиком** в удобное место, например `C:\work\revitmcp-kit`. Не
переименовывайте файлы внутри и не удаляйте `conventions.py` — без него
проверка не заработает.

Должно получиться:

```
C:\work\revitmcp-kit\
  revitmcp_kit.py        программа, которой вы будете пользоваться
  conventions.py         правила проверки (не трогать)
  INSTRUCTION.md         подробная версия этой инструкции
  README.md              краткая версия
  AGENTS.md              правила для ИИ-помощника
  .kilo\agents\          настройка агента
```

Проверьте, что набор запускается:

```powershell
cd C:\work\revitmcp-kit
python revitmcp_kit.py
```

Должен напечататься список команд. Если пишет «python не найден» —
используйте полный путь к `python.exe` из шага 2.2 вместо слова `python`.

### 2.4. Установите VS Code и Kilo Code

1. Установите VS Code, если его нет.
2. В VS Code откройте панель расширений (`Ctrl+Shift+X`).
3. Найдите **Kilo Code** и установите.
4. В настройках Kilo Code подключите модель — ключ и адрес даёт сопровождающий
   или ИТ.

### 2.5. Откройте папку набора в VS Code

Это важный шаг, его часто делают неправильно.

В VS Code: `Файл` → `Открыть папку` → выберите `C:\work\revitmcp-kit`. Именно
**папку набора**, а не отдельный файл. Только тогда Kilo Code автоматически
прочитает `AGENTS.md` и будет знать правила: какой диалект Python нужен, чего
нельзя делать, как проверять.

Проверка, что помощник видит правила — спросите его в чате:

```
Прочитай AGENTS.md и скажи одной фразой: чем отличается файл в revit_mcp
от файла в tools?
```

Правильный ответ по смыслу: *в `revit_mcp` — IronPython 3 внутри Revit, на
уровне языка Python 3.4, там нельзя f-строки и импорт хелперов только
относительный (`from .utils import ...`); в `tools` — обычный современный
Python 3, там можно всё.*

Если помощник этого не знает — он не прочитал правила. Проверьте, что открыта
папка, а не файл, и что `AGENTS.md` лежит в её корне.

**Настройка среды закончена.**

## 3. Прежде чем писать код

### 3.1. Решите, инструмент читает или пишет

Это главный вопрос, и отвечать на него нужно **до** написания кода.

- **Читает** — только смотрит модель и возвращает данные (сводка, проверка,
  поиск). Ничего не меняет.
- **Пишет** — создаёт, удаляет или изменяет элементы, ставит значения
  параметров.

От этого зависит устройство файла: читающий инструмент **не открывает
транзакцию**, пишущий обязан её открыть и правильно защитить (см. ниже).

Если сомневаетесь — почти всегда нужен читающий инструмент. Начните с него.

### 3.2. Два диалекта, не смешивать

| Файл | Где исполняется | Что можно |
|---|---|---|
| `revit_mcp/<domain>.py` | IronPython 3 внутри Revit, уровень языка Python 3.4 | только `"{}".format(x)`; **никаких** f-строк, `async`, `pathlib`, `list[str]`, современных аннотаций типов; хелперы — только относительным импортом `from .utils import ...` |
| `tools/<domain>_tools.py` | обычный современный Python 3 | всё современное — f-строки, `async`, типы |

F-строка в `revit_mcp/` — это `SyntaxError` при загрузке расширения: домен
не зарегистрируется, инструмент не появится, а в логах не будет ничего
внятного. Плоский импорт хелпера (`from utils import ...` без точки) —
ровно та же история: тихий отказ загрузки, только из-за импорта, а не
синтаксиса.

Каркас, который генерирует набор (глава 4), уже написан правильно — важно не
переписывать эти строки вручную.

### 3.3. Что запрещено

- Транзакция без `suppress_warnings(t)` сразу после `t.Start()`. Без него
  обычное предупреждение Revit открывает модальное окно и вешает сервер на
  всех станциях навсегда — пока кто-то не нажмёт кнопку руками.
- Транзакция в читающем маршруте — читающий маршрут не открывает транзакцию
  вообще.
- `.IntegerValue` и `DB.ElementId(<int>)`. Только `get_element_id_value()` /
  `make_element_id()` — на Revit 2027 голый `int` падает с «Multiple targets
  could match».
- `raise` из обработчика — всё тело в `try/except`, ответ только через
  `routes.make_response(data=..., status=...)`.
- Индексировать результат моста напрямую — он бывает `dict` или строкой
  `"Error: ..."`. Всегда через `format_response(response)`.
- `"status": "success"` с молча пропущенными элементами — считайте пропуски и
  отдавайте их в ответе.
- `import subprocess`, `socket`, `requests`, `shutil`, `eval`, `exec`, работа с
  файлами. Инструменту Revit это не нужно; если кажется, что нужно — сначала
  спросите сопровождающего.
- Правки любых файлов, кроме своих двух модулей.

Всё это уже вшито в шаблон и проверяется командой `check` (глава 6). Список
приведён здесь, чтобы вы понимали, *почему* так, а не только *что*.

## 4. Создайте каркас

```powershell
python revitmcp_kit.py new wall_report list_wall_report --get --author "Иван Иванов"
```

| Часть команды | Что это |
|---|---|
| `new` | создать каркас |
| `wall_report` | тема инструмента — домен; папка и файлы получат это имя |
| `list_wall_report` | имя, которым инструмент будет вызывать модель |
| `--get` | инструмент **читающий**. Для пишущего этот флаг просто не указывайте |
| `--author "Иван Иванов"` | вы, для истории изменений |

Имена — только строчные латинские буквы, цифры и подчёркивание. Никаких
пробелов, дефисов и русских букв. Хорошие имена инструментов начинаются с
глагола: `list_...`, `get_...`, `check_...`, `create_...`, `set_...`.

Появится папка `wall_report-tool`:

```
wall_report-tool\
  manifest.json                    кто автор, какие инструменты в пакете
  revit_mcp\wall_report.py         работа с моделью (внутри Revit)
  tools\wall_report_tools.py       описание для модели (снаружи)
  NOTES.md                         что сделали и как проверяли
```

Ровно эти файлы и должны получиться в итоге, ни больше ни меньше. Внутри
расставлены пометки `TODO` — это места, где нужны вы. Всё остальное уже
написано правильно: имена функций, структура, служебные строки. **Не
переименовывайте функции и не меняйте их аргументы** — по ним сервер находит
ваш инструмент.

## 5. Заполните TODO

### 5.1. Работайте с помощником

Перейдите в папку пакета:

```powershell
cd wall_report-tool
```

Хороший запрос помощнику выглядит так:

```
Заполни TODO в этом пакете.

Инструмент читающий: он собирает все стены модели, группирует их по типу
и считает суммарную площадь.

Возвращать: имя типа, количество стен, суммарную площадь в квадратных
миллиметрах. Плюс счётчик стен, площадь которых прочитать не удалось.

Параметр example — часть имени типа стены для фильтра, необязательный.
```

Чем точнее вы скажете, что должно вернуться и в каких единицах, тем меньше
придётся переделывать.

Что помощник сделает сам: структуру кода, служебные вызовы, обработку ошибок,
формат описания.

Что решаете только вы:

- какие элементы брать и по какому признаку;
- какие параметры читать — у экземпляра или у типа;
- что вернуть и в каких единицах;
- что считать ошибкой, а что — законным пустым ответом.

### 5.2. Заполните описание для модели

Докстринг инструмента в `tools/*_tools.py` — единственное, что языковая
модель видит перед вызовом. Из него строится схема, поэтому он пишется **для
модели**, а не для разработчика. Помощник напишет его сам, но прочитайте сами
и проверьте, что там есть все четыре вещи:

1. Когда этот инструмент вызывать.
2. Конкретные примеры значений — `"Generic - 200mm"`, а не «имя типа».
3. Единицы измерения — «площадь в квадратных миллиметрах».
4. **Ограничения прямым текстом.** Например: «стены в связанных моделях не
   учитываются», «витражные стены считаются как одна стена».

Четвёртый пункт — самый важный, и его чаще всего забывают. Без него модель
примет пустой ответ за доказательство, что таких стен в проекте нет, и
сообщит пользователю неверный вывод о модели.

### 5.3. Заполните manifest.json и NOTES.md

В `manifest.json` замените `TODO` в поле `description` на одну строку о
назначении. Проверьте, что в `author` стоит ваше имя.

`NOTES.md` заполните честно: на какой модели проверяли, какая версия Revit,
что осталось непроверенным. Это читает сопровождающий, и это единственное
место, где можно предупредить его о слабом месте.

## 6. Тестирование

Проверок две, и они разные по смыслу. Обе обязательны, и ни одна не заменяет
другую.

| | `check` | `probe` |
|---|---|---|
| Что смотрит | форму кода: диалект, импорты, докстринг, сигнатуры | поведение: реальные данные с реальной модели |
| Нужен ли Revit | нет | да, открытый Revit с открытой моделью |
| Что доказывает | код *может* загрузиться на станции | инструмент *действительно* возвращает то, что нужно |

> **Важно.** Зелёная проверка формы — это не «работает». Работает — это
> `PROBE_OK` с данными, на которые вы посмотрели и признали правильными.

### 6.1. `check` — проверка формы

```powershell
python ..\revitmcp_kit.py check
```

Если всё хорошо, напечатает `Замечаний нет.` Если есть замечания, читайте
формулировки буквально — они точные. Частые:

| Замечание | Что это значит |
|---|---|
| `f-strings need Python 3.6+` | В файле внутри Revit использована f-строка. Нужен `"{}".format(x)`. |
| `import package modules relatively` | Хелпер импортирован плоско (`from utils import ...`). Нужно `from .utils import ...`. |
| `остались TODO в докстринге` | Не заполнено описание для модели. Без него инструмент непригоден. |
| `не заполнено description` | В `manifest.json` осталось `TODO`. |
| `Args: block` | В описании не перечислены все параметры. |
| `use make_element_id()` | Использован запрещённый способ работы с номерами элементов — падает на Revit 2027. |

Самый простой способ исправить: скопируйте текст замечания целиком и отдайте
помощнику. Повторяйте, пока не будет `Замечаний нет.`

`check` использует ровно тот же код, что и приёмка у сопровождающего —
поэтому сдавать пакет с замечаниями бессмысленно, приёмка откажет теми же
словами.

### 6.2. `probe` — проверка поведения на живой модели

**Это главная проверка.** `check` смотрит только на форму кода — он не знает,
правильные ли данные возвращает ваш маршрут.

Убедитесь, что Revit открыт и модель открыта. Затем:

```powershell
python ..\revitmcp_kit.py probe
```

Для пишущего инструмента или если нужны параметры:

```powershell
python ..\revitmcp_kit.py probe --payload '{"example": "Generic"}'
```

Что происходит: текст вашего маршрута отправляется в `/execute_code/`
**вашего собственного** Revit и выполняется на **реально открытой модели**.
Репозиторий для этого не нужен, Revit перезапускать не надо.

Ожидаемый результат: строка `PROBE_OK:` и за ней данные. Посмотрите на данные
глазами:

- Похожи ли числа на правду? Столько ли элементов, сколько вы ожидали?
- Единицы действительно миллиметры, а не футы? Если числа расходятся
  примерно в 305 раз — это ровно перепутанные единицы (внутри Revit всё в
  футах, наружу — только миллиметры).
- Кириллица не превратилась в `?????` — русские имена типов и элементов
  должны дойти целиком.

Если ошибка:

| Что видите | Что делать |
|---|---|
| `мост не отвечает` | Revit закрыт или модель не открыта. Проверьте шаг 2.1. |
| `Маршрут упал внутри Revit` + текст ошибки | Отдайте помощнику весь текст, включая трассировку. |
| `PROBE_OK`, но данные пустые | Логика не находит элементы. Проверьте категорию и фильтр. |
| `PROBE_OK`, но числа неправдоподобные | Скорее всего перепутаны единицы. |

### 6.3. Необязательный собственный тест

Если хотите оставить после себя что-то более прочное, чем «я один раз
проверил и оно сработало», положите рядом файл `tests/test_<domain>.py`,
например `wall_report-tool/tests/test_wall_report.py`.

Требования к нему такие же, как у всего набора: только стандартная
библиотека, без `pytest` — контрибьютор не обязан ставить что-то ещё. Простой
рабочий образец: обычный скрипт, который сам себя запускает, использует тот
же приём, что и `probe` (текст маршрута в `/execute_code/` своего Revit), и
печатает `TEST_OK` или падает с понятным сообщением, если данные не сошлись с
ожиданием.

Этот файл необязателен, но если он есть — `pack` (глава 7) автоматически
включит его в архив. Сопровождающий сам решает, запускать ли его при приёмке;
для вас его главная польза в том, что при следующем изменении общего кода
именно он первым покажет, что что-то отвалилось.

### 6.4. Чек-лист перед сдачей

- [ ] `check` — без замечаний.
- [ ] `probe` — `PROBE_OK` с данными, которые вы посмотрели глазами и
      признали правильными.
- [ ] Докстринг инструмента содержит все четыре вещи из шага 5.2.
- [ ] `manifest.json`: `author` и `description` заполнены, без `TODO`.
- [ ] `NOTES.md`: честно указана модель проверки и что осталось непроверенным.
- [ ] Единицы наружу — миллиметры.
- [ ] Кириллица в тестовых данных дошла без искажений.

Команда сначала сама перепроверит форму (`check`) и откажется собирать пакет
с замечаниями. Получится файл `wall_report.zip` — ровно ваши два модуля,

### 7.2. Положите в папку приёма

```
\\srv-dfs\BIM\01_Ресурсы плагинов\827_RevitMCP\inbox\
```

Просто скопируйте туда `.zip`. Всё.

### 7.3. Что происходит дальше

1. Сопровождающий запускает приёмку — она проверяет пакет теми же правилами,
   что и ваш `check`, и отдельно ищет опасные конструкции.
2. Сопровождающий **читает ваш код**. Это обязательный шаг: код будет
   исполняться внутри Revit на всех станциях отдела, а автоматика не может
   оценить замысел.
3. Если всё в порядке, код попадает в репозиторий, ваше имя сохраняется в
   истории изменений.
4. Инструмент приезжает людям при следующем перезапуске Revit и входе в
   систему. Ничего никому дополнительно делать не нужно.

Если что-то не так, сопровождающий вернёт пакет с замечаниями. Исправьте и
соберите заново.

## 8. Частые ошибки

**Открыли в VS Code отдельный файл, а не папку набора.** Помощник не читает
`AGENTS.md` и пишет код, который не пройдёт проверку. Открывайте папку.

**Начали писать код, не решив, инструмент читает или пишет.** Переделывать
придётся почти всё. Решите сначала (шаг 3.1).

**Правили `conventions.py`, чтобы проверка прошла.** Это копия файла, по
которому сдачу проверяет сопровождающий. У вас `check` пройдёт, приёмка
откажет — расхождение сразу видно.

**Сдали по зелёному `check`, не запустив `probe`.** Самая частая причина
возврата пакета — форма верна, а данные неверны или пусты.

**Добавили в пакет что-то ещё** — правку общего файла, второй модуль, файл с
данными. Приёмка отклонит архив целиком. Пакет — это ровно два модуля (плюс
необязательный тест). Если задача требует большего, напишите сопровождающему
**до** того, как писать код.

**Перепутали единицы.** Внутри Revit всё в футах, наружу всё в миллиметрах.
Если числа отличаются примерно в 305 раз — дело в этом.

**Использовали плоский импорт хелпера** (`from utils import ...` без точки)
вместо относительного. Работает на первый взгляд одинаково, но под
IronPython 3 такой импорт не грузится — домен пропадает молча, и в логах
ничего не будет.

**Использовали кнопку Reload в pyRevit.** Для этого расширения она не
годится и роняет весь Revit. Только полный перезапуск. Для проверки своего
кода перезапуск вообще не нужен — используйте `probe`.

## 9. Словарь терминов

| Термин | Что это |
|---|---|
| Мост | HTTP-сервер внутри Revit на порту `48884`. С ним разговаривает `probe` и проверяется статус на `/revit_mcp/status/`. |
| Домен | Тема вашего инструмента (`wall_report`, `audit`). Задаёт имена файлов и папок. |
| `check` | Проверка формы кода: диалект, импорты, докстринг, сигнатуры. Не требует Revit. |
| `probe` | Прогон вашего маршрута на реально открытой модели через `/execute_code/`. Требует открытый Revit. |
| `pack` | Сборка готового `.zip` для сдачи. Сначала сам перезапускает `check`. |
| Папка приёма (`inbox`) | Сетевая папка, куда контрибьютор кладёт готовый `.zip`. Запись — контрибьюторам, чтение — сопровождающему. |
| Сопровождающий | Единственный, у кого есть доступ к репозиторию сервера. Читает код, одобряет и публикует. |
| `manifest.json` | Файл пакета с именем автора, доменом, списком инструментов и описанием. |
| `NOTES.md` | Заметки контрибьютора: на чём проверяли, что осталось сомнительным. |
