# get_view возвращал 404 на именах видов с пробелами

**Статус:** исправлено · коммит `67644ee`

## Симптом

`get_revit_view` с именем вида «Level 1» возвращал 404. И почти любой другой вид тоже —
потому что в Revit имена видов с пробелами это норма, а не исключение.

## Причина

Маршрут `GET /get_view/<view_name>` получает имя в **path-параметре**, а значит оно
приходит URL-закодированным: `Level%201`. Обработчик сравнивал полученную строку с
именами видов напрямую, поэтому «Level%201» не совпадал ни с чем.

То есть баг был не в Revit и не в логике поиска вида, а на границе HTTP — на единственном
маршруте проекта, который вообще использует path-параметр со свободным текстом.

## Исправление

Декодирование сразу на входе, до любого сравнения:

```python
from urllib import unquote
...
# URL-decode the path parameter first (e.g. "Level%201" -> "Level 1").
view_name = unquote(view_name)
```

`from urllib import unquote` — это Python 2 форма, обязательная для IronPython
([[Revit-часть написана на IronPython 2.7 и не может делить код с MCP-частью]]).
В Python 3 это было бы `urllib.parse.unquote`.

## Урок

> Path-параметр со свободным текстом всегда приходит закодированным. Декодируйте его
> первой строкой обработчика, до сравнений, поиска и логирования.

В проекте таких маршрутов ровно два: `/get_view/<view_name>` и
`/element_properties/<element_id>`. Второй безопасен, потому что числовой ID не
содержит символов, требующих кодирования. Любой новый маршрут с текстовым
path-параметром обязан начинаться с `unquote`.

Более общий вывод: баг вида «работает на моих тестовых данных, падает на реальных»
часто прячется именно в тестовых данных. «Level 1» — дефолтное имя в Revit; тестировали,
видимо, на видах, названных без пробелов.
