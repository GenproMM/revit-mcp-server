# Выпуск релиза: сборка, пилот, раскатка

Пошаговая инструкция для сопровождающего. От закоммиченного кода до работающего
RevitMCP у пилотных, а затем у всех пользователей.

Здесь только порядок действий и критерии «пройдено». Детали, которые не
повторяются:

- первичная настройка сервера, права, выбор пилотных людей — [SETUP-RUNBOOK.md](SETUP-RUNBOOK.md);
- что делает пользователь и как разбирать отказы — [USER-GUIDE.md](USER-GUIDE.md);
- устройство папок, откат, подводные камни — [README.md](README.md);
- протокол чекпоинтов, Ledger и схема тегов — `.planning/RELEASES.md`.

Пометки: **[Вы]** — сопровождающий, **[Пилот]** — пилотный пользователь,
**[Все]** — пользователи при раскатке. Пометка «не проверено вживую» стоит там,
где утверждение следует из кода, а не из прогона.

---

## Схема в одном экране

```
 1. Подготовка      тег release/Rn-rcK на коммите, push ветки и тега
 2. Сборка в ПИЛОТНЫЙ share      обе половины, гейты скриптов не обходить
 3. Пилотная машина              снять старый путь расширения, установить с пилотного share
 4. Приёмка пилота               чек-лист ниже; срок и критерий называете вы
 5. Промоушен                    тег release/Rn на ТОТ ЖЕ коммит, публикация в основной share
 6. Раскатка                     пользователи обновляются сами; вы следите за update.log
 7. Фиксация                     Ledger, сессионная заметка
```

Если пилот нашёл дефект: исправление, новый тег `release/Rn-rc(K+1)`, возврат к
шагу 2. Тег `release/Rn` в этом случае **не ставится**.

В основной share до шага 5 не публикуется ничего: публикация туда доходит до
всех установленных машин при следующем входе и следующем перезапуске Revit.

## 0. Что должно быть готово до начала

| Условие | Как проверить |
|---|---|
| Выпускаемый коммит закоммичен, дерево чисто по отгружаемым путям | `git status --short -- revit_mcp tools startup.py bridge.py main.py server.py deploy tests extension.json` ничего не печатает |
| Тесты зелёные целиком | `uv run pytest tests/unit` |
| Холодный старт < 2.0 с | `uv run python tests/test_init_latency.py` печатает `INIT_LATENCY_S=…` |
| Обе половины в коммите согласованы | `git show <коммит>:bridge.py` содержит `BASE_URL = …/genpro_revit_mcp`, `git show <коммит>:startup.py` содержит `routes.API("genpro_revit_mcp")` |
| Имя пилотного share выбрано | см. шаг 1.2 |
| Пилотная машина выбрана | см. шаг 3 |

На момент написания коммит-кандидат R1 — `6a03f85` на ветке
`feature/local-revit-mcp-tools` (все условия выше выполнены). Если после него
появились коммиты, тегируйте именно тот, который хотите выпустить, и повторите
проверки.

## 1. Подготовка

### 1.1. Тег-кандидат и push [Вы]

Тег и push делаете вы: это решение, а не автоматика.

```bat
git tag -a release/R1-rc1 -m "R1 release candidate 1" <коммит>
git push origin feature/local-revit-mcp-tools release/R1-rc1
```

Ветка опережает `origin` на десятки коммитов, это нормально: сборочный сервер
делает `git pull` именно с неё.

### 1.2. Пилотный share [Вы]

Отдельная папка рядом с `06_RevitMCP`. Требования те же, что у `MCP_SHARE_ROOT`:
ASCII, без пробелов, **вне любого git-репозитория**, пользователям — чтение,
вам — запись. Например `\\srv-dfs\BIM\06_RevitMCP_pilot`. Создавать `ext\`,
`install\`, `payload\` внутри не нужно: их создадут скрипты.

Секрет у пилота свой: `MCP_SECRET_FILE` по умолчанию лежит в
`<share>\_build\bridge_secret`, создаётся один раз при первой публикации и после
не перезаписывается. В R1 секрет **ничего не проверяет** (проверка включается в
фазе 5), так что отличие пилотного секрета от флотского сейчас безвредно.

## 2. Сборка в пилотный share [Вы, на сборочном сервере]

На сборочном сервере должны быть Windows x64, `git`, `uv`, доступ к PyPI или
зеркалу и **установленный pyRevit** (колёса собираются под его CPython). Всё это
перечислено в SETUP-RUNBOOK.md, раздел 3.

Одна сессия cmd, все команды подряд:

```bat
chcp 65001
set "MCP_SHARE_ROOT=\\srv-dfs\BIM\06_RevitMCP_pilot"
pushd "\\srv-dfs\BIM\06_RevitMCP\revit-mcp-server"
git fetch --tags
git checkout release/R1-rc1

deploy\publish-extension.cmd
deploy\build-payload.cmd
popd
```

`set MCP_SHARE_ROOT` обязателен **до** запуска скриптов и в той же сессии:
`config.cmd` подставляет значение по умолчанию (основной share) только если
переменная не задана. Если забыть, публикация пойдёт в основной share, то есть
сразу ко всем. Перед первой публикацией убедитесь, что в выводе строка `to  :`
указывает на пилотный share.

Собирайте с тега, а не с произвольного состояния дерева. Если скрипты печатают
`WARNING: uncommitted change` или `building from a dirty tree` — остановитесь:
`VERSION` не будет описывать собранное. Релизная сборка из грязного дерева
сейчас только предупреждается, не блокируется.

**Что должно быть в выводе:**

| Шаг | Ожидаемо |
|---|---|
| `publish-extension.cmd` | строка `to  : …06_RevitMCP_pilot\ext\revit-mcp-server.extension`; в конце `Published.` и список `extension.json`, `startup.py`, `LICENSE`, `revit_mcp`, `_manifest.json` (если списка нет, см. раздел «Если что-то не так») |
| `build-payload.cmd`, гейт | `SECRET=ok (…)`, `INIT_LATENCY_S=` меньше 2.0, `TOOLS=59`, `MANIFEST=ok (59 tools)`, `GATE_OK`, затем `Done. payload <VERSION> published` |

Слово `Published` само по себе не доказательство (SETUP-RUNBOOK.md, раздел 4).
Проверьте отдельными командами:

```bat
dir "\\srv-dfs\BIM\06_RevitMCP_pilot\ext\revit-mcp-server.extension"
dir "\\srv-dfs\BIM\06_RevitMCP_pilot\install"
type "\\srv-dfs\BIM\06_RevitMCP_pilot\payload\VERSION"
type "\\srv-dfs\BIM\06_RevitMCP_pilot\payload\ENGINE"
powershell -NoProfile -Command "(Get-Content -Raw '\\srv-dfs\BIM\06_RevitMCP_pilot\ext\revit-mcp-server.extension\_manifest.json' | ConvertFrom-Json).commit"
git rev-parse release/R1-rc1^{commit}
```

- в `ext\…` лежат `extension.json`, `startup.py`, `LICENSE`, `revit_mcp\`, `_manifest.json`; в `install\` — `install.cmd`, `update.cmd`, `find-python.cmd`, `check_routes_config.py`;
- `VERSION` вида `2026.10.24-0910.<sha>`, где `<sha>` — начало хеша тега. Имя релиза в `VERSION` пока **не встраивается** (схема версий из RELEASES.md ещё не реализована), поэтому сопоставляйте тег и сборку по этому sha;
- `commit` из манифеста совпадает с хешем коммита тега (последняя команда). Именно `^{commit}`: у аннотированного тега `git rev-parse` без него печатает хеш самого тега, и сверка не сойдётся.

Запишите три значения: `VERSION`, `ENGINE`, хеш коммита. Они понадобятся при
приёмке и при откате.

После сборки верните рабочую копию на ветку:

```bat
pushd "\\srv-dfs\BIM\06_RevitMCP\revit-mcp-server"
git checkout feature/local-revit-mcp-tools
popd
```

**Осторожно: `publish-extension.cmd` сначала удаляет `ext\…`, и только потом
копирует и пишет секрет и манифест.** Если скрипт упал посреди работы, в `ext\`
остаётся неполное дерево. Для пилотного share это неважно, перезапустите
скрипт. Для основного share это важно, см. шаг 5.

## 3. Пилотная машина [Вы + Пилот]

### 3.1. Кого брать

Двух-трёх людей: обычные права, зажатая машина (AppLocker/EDR, нет планировщика
задач), по возможности русская модель. Подробности — SETUP-RUNBOOK.md, раздел 6.

У каждого заранее: Revit 2024–2027, pyRevit **для этого пользователя**
(5.x или новее), Hermes, чтение на пилотный share.

**Для R1 обязательно: хотя бы одна машина с чистой установкой через
`install.cmd` и с чужим MCP рядом** (`revit-mcp.extension`, API `/revit_mcp/`).
Параллельная установка не проверялась вживую, пилот — это её первая проверка.

### 3.2. Снять старый путь, если машина уже была установлена [Вы]

Это самый вероятный источник путаницы. `install.cmd` **добавляет** путь
пилотного share, но **не снимает** путь основного: он принципиально не
отключает и не забывает чужие пути. Если на машине уже стоит наша прежняя
установка, в pyRevit окажутся два пути с одним и тем же именем
`revit-mcp-server.extension`.

- Чистая машина (никогда не ставили) — этот шаг не нужен.
- Уже установленная машина: перед установкой посмотрите пути
  (`userextensions` в `%APPDATA%\pyRevit\pyRevit_config.ini`, **только читать**),
  убедитесь, что путь `…\06_RevitMCP\ext` наш, и снимите его через CLI:

  ```bat
  pyrevit extensions paths forget "\\srv-dfs\BIM\06_RevitMCP\ext"
  ```

  Файл конфига руками не править. Чужие пути не трогать.
- Если на машине есть локальная папка `%APPDATA%\pyRevit\Extensions\revit-mcp-server.extension`,
  `install.cmd` остановится: «needs manual path review». Это не ошибка
  установщика: проверьте, что это за папка (в репозитории разработчика это
  junction на рабочую копию, на пилотной машине её быть не должно), и решайте
  вручную.

Как поведёт себя pyRevit с двумя путями одного имени — не проверено вживую,
поэтому лучше не создавать такую ситуацию.

### 3.3. Снимки «до» [Вы + Пилот]

Пока Revit открыт со старой установкой, сохраните ответы **обоих** API:

- чужой: `http://127.0.0.1:48884/revit_mcp/status/?verbose=true`;
- наш (старый, если стоял): тот же адрес.

После установки сравните: чужой статус должен остаться прежним, меняется только
наш. Диспетчер pyRevit у двух MCP общий, поэтому проверяйте их **по очереди**, не
одновременно (README.md, раздел «Coexistence»).

## 4. Установка на пилоте [Пилот]

Дайте пилотному пользователю ровно это:

> 1. Заверши текущие обращения помощника к Revit.
> 2. Открой `\\srv-dfs\BIM\06_RevitMCP_pilot\install\` и запусти `install.cmd`.
> 3. Прочитай вывод до конца. При ошибке ничего не перенастраивай, пришли вывод.
> 4. Согласованно перезапусти Revit **полностью** (Reload не подходит), открой модель.
> 5. Зарегистрируй наш сервер в Hermes по USER-GUIDE.md, раздел «Настройка MCP в Гене». Чужую запись MCP не заменяй.
> 6. Открой `http://127.0.0.1:48884/genpro_revit_mcp/status/?verbose=true` и пришли ответ целиком.

Что должен сказать установщик:

| Шаг | Ожидаемо |
|---|---|
| `[1/6]` | `ok, running on CPY3123` (или другой движок из `payload\ENGINE`) |
| `[2/6]` | `Shared Routes unchanged: 127.0.0.1:<порт>`; строка `OUR extension path registered and enabled; other extensions unchanged` |
| `[4/6]` | `scheduled task created` **или** `autostart entry created`. Строка `WARNING: no automatic updates` означает, что на этой машине обновления сами не придут: решать с ИТ |

Установщик остановится, а не продолжит, если Routes выключен или не на
`127.0.0.1`, если pyRevit старше 5.x, если есть локальная одноимённая папка
расширения. Это штатные остановки: ничего не отключено и не изменено.

Hermes-запись ручная и установщиком не создаётся. Порт из строки `[2/6]` нужно
подставить в `REVIT_PORT` нашей записи.

## 5. Приёмка пилота [Вы]

Пилот пройден, если выполнено **всё**. Заполните таблицу по каждой машине.

### 5.1. Один слушатель и состояние расширения

| Проверка | Как | Пройдено, если |
|---|---|---|
| Один Revit на порту | PowerShell: `Get-NetTCPConnection -LocalPort 48884 -State Listen` | ровно одна строка (два слушателя дают ложные результаты, закройте лишний Revit; запись о числе слушателей нужна в отчёте) |
| Расширение загрузилось | `http://127.0.0.1:48884/genpro_revit_mcp/status/?verbose=true` | `api_name = genpro_revit_mcp`, `"health": "healthy"`, нет ключа `failed_domains` |
| Модули-помощники не считаются ошибкой | то же | в `skipped_modules` ожидаемо `identity`, `integrity`, `registry`, `textutils`, `trust`, `utils` с причиной `no register_*_routes callable`; в `failed_domains` их быть не должно |
| Документ виден | то же | `document_title` — имя открытой модели; если русское, читается, а не `?????` |
| Чужой MCP не затронут | `http://127.0.0.1:48884/revit_mcp/status/?verbose=true` | ответ совпадает со снимком «до» |

Число доменов берите из ответа и сравнивайте со снимком, а не с числом из
старых документов: цифра `domains_registered: 23` в SETUP-RUNBOOK.md устарела.

### 5.2. Сервер и Гена

| Проверка | Пройдено, если |
|---|---|
| Инструменты Revit видны в Гене | в списке 59 инструментов (`tests/unit/tool_manifest.txt`) |
| `get_revit_status` | отвечает, называет порт и документ |
| Чтение | например `list_levels` или `get_revit_model_info` на открытой модели; кириллические имена приходят целыми |
| Запись | только на тестовой модели; один обратимый вызов, результат проверен в Revit глазами |

### 5.3. Установка и обновления

| Проверка | Пройдено, если |
|---|---|
| Версия на машине | `type "%LOCALAPPDATA%\RevitMCP\current-version.txt"` равна `VERSION` из шага 2 |
| Автообновление | вывод установщика на `[4/6]` — `scheduled task created` или `autostart entry created` |
| Обновление работает | пересоберите payload (новый тег `rcK+1` или повтор), на машине запустите ярлык **Update RevitMCP**: в `%LOCALAPPDATA%\RevitMCP\update.log` запись `now at <новая версия>`, `current-version.txt` изменился |
| Откат возможен | в `%LOCALAPPDATA%\RevitMCP\versions\` больше одной версии |

### 5.4. Что записать в отчёт пилота

Это закрывает пробелы, которые остались после живой пробы D-04:

- версии **Revit** и **pyRevit** на каждой машине;
- число слушателей на 48884;
- дата и время приёмки;
- у чистой установки с чужим MCP рядом: что именно стояло рядом, и что чужой статус не изменился.

### 5.5. Срок и критерий «можно выкатывать на всех» [Вы называете]

Для R1 тип чекпоинта OFFER, но шаг пилота обязателен, и **срок наблюдения и
критерий называете вы**; без этого шаг не считается пройденным. Предложение для
вашего решения (не договорённость): 2–3 рабочих дня на 2–3 машинах, ноль
блокирующих замечаний, `update.log` без `ERROR`, не меньше одного успешного
ручного обновления, одна чистая установка с чужим MCP рядом. Подтвердите или
замените.

### 5.6. Если приёмка не пройдена

Не ставьте `release/R1`. Назовите причину по таблице в разделе «Если что-то не
так», исправьте, поставьте `release/R1-rc2`, вернитесь к шагу 2.

## 6. Промоушен в основной share [Вы]

Только после пройденного пилота и только на **тот же коммит**, что у
пилотного тега.

### 6.1. Перед публикацией

1. **Запишите адрес отката.** Что сейчас лежит в основном share — единственный
   снимок того, к чему возвращаться (в `ext\` его нет, в `payload\` хранится одна
   прошлая версия на каждой машине, не на сервере):

   ```bat
   type "\\srv-dfs\BIM\06_RevitMCP\payload\VERSION"
   type "\\srv-dfs\BIM\06_RevitMCP\payload\ENGINE"
   ```

   По sha из `VERSION` найдите коммит, из которого собрана текущая раздача.

2. **Согласуйте окно.** В R1 меняется пространство имён Routes: было
   `/revit_mcp/`, стало `/genpro_revit_mcp/`. Обе наши половины должны обновиться
   вместе, а они доезжают в разное время:
   - Revit-половина загружается с общего пути при **каждом полном перезапуске Revit**;
   - CPython-половина обновляется **через несколько минут после входа** в систему
     (или по ярлыку Update RevitMCP).

   Пока одна половина новая, а другая старая, вызовы идут на несуществующий
   адрес и падают с «Route does not exist». Это следует из кода и **не
   проверялось вживую**. Поэтому публикуйте вне рабочего времени или объявите
   окно, и скажите пользователям делать порядок: **Update RevitMCP → перезапуск
   Гены → полный перезапуск Revit**.

3. Убедитесь, что `MCP_SHARE_ROOT` **не задан** (в новой сессии cmd) или задан
   на основной share, и что строка `to  :` в выводе будет `…\06_RevitMCP\ext\…`.

### 6.2. Публикация

```bat
chcp 65001
pushd "\\srv-dfs\BIM\06_RevitMCP\revit-mcp-server"
git fetch --tags
git tag -a release/R1 -m "R1" release/R1-rc1^{commit}
git push origin release/R1
git checkout release/R1

deploy\publish-extension.cmd
deploy\build-payload.cmd

git checkout feature/local-revit-mcp-tools
popd
```

Тег `release/R1` ставится на коммит тега-кандидата (`release/R1-rcK^{commit}`),
а не на HEAD. Пересборка даст новую метку `VERSION` (другое время), но тот же коммит.

Порядок: сначала расширение, сразу за ним payload. Ни один порядок не убирает
окно рассогласования (см. 6.1), поэтому **между скриптами не должно пройти много
времени**. Основной share содержит первый секрет: при первой
публикации сюда создаётся `…\06_RevitMCP\_build\bridge_secret`. Он нужен только
фазе 5, но запомните, что копию секрета видит каждый, кто читает share.

`publish-extension.cmd` сначала удаляет `ext\…`, потом копирует. Пока он
работает, пользователь, запускающий Revit, может загрузить пустое или неполное
расширение. Сразу после скрипта проверьте результат так же, как на шаге 2
(`dir`, `commit` в манифесте, `VERSION`). Если `ext\` оказался неполным —
запустите скрипт ещё раз, не оставляйте так.

## 7. Раскатка пользователям

Отдельные действия от пользователей **не нужны** — это и есть смысл схемы.

### 7.1. Кто как получает релиз

| Кто | Что происходит |
|---|---|
| Уже установленный пользователь | CPython-половина обновляется через несколько минут после входа; Revit-половина — при полном перезапуске Revit. Запись в Hermes не меняется: путь `current\app\server.py` тот же |
| Новый пользователь | `install.cmd` с основного share, затем регистрация в Hermes по USER-GUIDE.md |
| Ноутбук вне офиса | обновление пропускается тихо, приедет при следующем входе в офисе |

Пользователь, у которого основной путь ещё зарегистрирован — это нормально, он
остаётся на основном share. Пилотные машины, которые ставили с пилотного share,
нужно перевести обратно: снять путь пилота
(`pyrevit extensions paths forget "<пилот>\ext"`), запустить `install.cmd` с
основного share, перезапустить Revit.

### 7.2. Сообщение пользователям [Все]

Отправьте перед публикацией:

> Сегодня в HH:MM обновляется RevitMCP. Менять ничего не нужно, но после
> обновления нужен один раз такой порядок:
> 1. Меню Пуск → **Update RevitMCP**, дождитесь «updated».
> 2. Перезапустите Гену (или `/reload-mcp`).
> 3. Закройте Revit **полностью** и откройте заново.
>
> До шага 3 инструменты Revit могут отвечать ошибкой «Route does not exist». Это
> ожидаемо. Если после шага 3 ошибка осталась, пришлите ответ
> `http://127.0.0.1:48884/genpro_revit_mcp/status/?verbose=true` и содержимое
> `%LOCALAPPDATA%\RevitMCP\update.log`.

### 7.3. Что смотреть после выпуска [Вы]

- первые часы: сообщения пользователей с «Route does not exist» (ожидаемо в окне) и всё, что осталось после полного перезапуска;
- `health: degraded` у пользователей — по `failed_domains` в ответе статуса;
- застрявшие на старой версии: `update.log`, затем ярлык Update RevitMCP вручную.

Что просить прислать: ответ статуса целиком, `update.log`, версию pyRevit,
`payload\ENGINE` (USER-GUIDE.md, «Что прислать сопровождающему»).

## 8. Откат

**На одной машине (быстро):** вернуть junction на предыдущую версию. `rmdir` без
`/s`:

```bat
rmdir "%LOCALAPPDATA%\RevitMCP\current"
mklink /J "%LOCALAPPDATA%\RevitMCP\current" "%LOCALAPPDATA%\RevitMCP\versions\<старая>"
echo <старая>>"%LOCALAPPDATA%\RevitMCP\current-version.txt"
```

Хранится одна прошлая версия. Это откатывает только CPython-половину.

**У всех:** пересобрать **обе** половины из коммита, который вы записали в шаге
6.1, и опубликовать так же, как в 6.2 (checkout старого коммита или тега,
`publish-extension.cmd`, затем `build-payload.cmd`). Пересборка даёт новую метку
`VERSION`, поэтому машины заберут её как обновление. Revit-половина вернётся при
следующем полном перезапуске Revit. Откат тоже меняет пространство имён, то есть
в нём то же окно рассогласования, что и в 6.1.

Тег `release/R1` после отката не удаляйте: запишите в Ledger, что выпуск откатан
и почему.

## 9. Если что-то не так

| Симптом | Что делать |
|---|---|
| `Published`, но `dir` пуст или список короткий | `MCP_SHARE_ROOT` ASCII? `chcp 65001` в той же сессии? Смотри SETUP-RUNBOOK.md, раздел 10 |
| В списке `ext\…` нет `_manifest.json` | `make_manifest.py` упал: обычно непривязанный `.py` в `revit_mcp/` (закоммитьте или удалите) или сбой `git ls-files`. После падения `ext\` пустой, перезапустите скрипт |
| `ERROR: could not stage the shared secret` | файл секрета повреждён (пустой, с BOM, не ASCII): сообщение называет путь и дефект, но не значение. Исправьте файл или удалите его, чтобы создался новый (это ротация: придётся пересобрать обе половины и перезапустить Revit у всех, см. `config.cmd`) |
| `SECRET=failed` в гейте | `ext` и `app` содержат разные секреты: опубликуйте обе половины из одного `MCP_SECRET_FILE` |
| `install.cmd`: «needs manual path review» | локальная папка расширения, см. шаг 3.2 |
| `install.cmd`: «Routes must already be enabled on 127.0.0.1» | общие настройки Routes чужие, менять нельзя: согласуйте с владельцем. Проверяйте по логу `pyRevit_<год>_<PID>_runtime.log` строку `Routes server is listening on http://127.0.0.1:…`; на первой пилотной машине в 2026-09-07 было `0.0.0.0` |
| `Route does not exist` у пользователя | сначала проверьте окно рассогласования половин (6.1), потом полный перезапуск Revit; затем `disabled = true` в `[revit-mcp-server.extension]` (SETUP-RUNBOOK.md, раздел 10) |
| `health: degraded` | `failed_domains` в ответе статуса называет домен и исключение |
| Стоит старая версия | `%LOCALAPPDATA%\RevitMCP\update.log`, затем ярлык Update RevitMCP |
