<objective>
Close follow-up items 1 and 2 of `01-04-SUMMARY.md`: apply the user's d27-b decision to
`bridge.py`. Every call issued through this MCP server process takes the lock except GET
`/status/`; GET reads, `/model_info/`, `revit_image` and the five POST routes of the D-08
read-only allowlist all queue. The allowlist (`READ_ONLY_POST`) is removed because it is the
measured `cross-wired-read`, and its unit tests are replaced by tests that pin the new rule.

Purpose: the 01-04 bench measured that pyRevit's one shared request handler cross-wires
overlapping requests: the overlapped request answers 200 with the other request's output and
its own body never runs. An unlocked read overlapping a mutation (threat T-01-10, high) is
therefore a real way to lose a write while reporting success. SER-01 holds for mutations
only if nothing else from this process can overlap them; SER-02 narrows to "does not block
`/status/`" (the requirement text itself is updated by plan 01-08, the docs by plan 01-07).

Output: `bridge.py` (lock coverage, one serialized path for `_revit_call` and `revit_image`,
wording), `tests/unit/test_bridge_serialization.py` (tracer through the tool layer, classifier,
waits-while-locked, drift scan).
</objective>

Detector signals: pluralization ("second" waiting call) and chosen ("configurable" port).

- **Primary noun:** the Revit *target* `REVIT_HOST:REVIT_PORT`, exactly one per MCP server
  process (D-02), unchanged by this plan.
- **What generalises here:** the thing the lock serializes. It was "a mutating POST"; the
  bench showed it must be "any call that enters pyRevit's shared request handler", of which
  mutations are one subset. **Decision: `promote`.** The lock's coverage, its wait message and
  its queue-busy message are re-expressed in terms of a *call* to Revit; "mutation" is demoted
  to one kind of call. Nothing is added alongside: the read-only allowlist is deleted, not kept
  as a parallel path.
- **Target count:** `no-change` in Phase 1. One process = one target = one module-global lock
  (D-02, D-07). Recorded, not built here: once Phase 2 lets one server address several Revit
  instances per call (decision a5-a), the lock must be promoted to one lock per target, keyed by
  `host:port`. Plan 01-08 writes that into ROADMAP Phase 2 so it is not lost.
- **Invariant test (accepted):** `test_unlocked_every_tool_endpoint_except_status_is_locked`
  scans every tool endpoint, so a future tool or a widened `UNLOCKED_GET` fails the suite.
  Suggested for Phase 2 (not built here): a test that calls to two different targets do not
  serialize against each other while calls to one target do.
</assumption_delta_decision>
