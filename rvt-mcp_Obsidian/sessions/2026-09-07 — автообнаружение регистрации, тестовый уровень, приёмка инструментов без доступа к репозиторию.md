# 2026-09-07 — автообнаружение регистрации, тестовый уровень, приёмка инструментов без доступа к репозиторию

## Контекст задачи

Пользователь готовит две вещи: аудит моделей по загружаемой конфигурации и
подключение нескольких разработчиков инструментов **без доступа к
репозиторию** — они адресуют пакеты на сборку, а не пушат сами. Разработчики —
малоопытные «вайбкодеры» на Kilo Code с китайскими моделями в VS Code и в
Hermes. Задача: спроектировать архитектуру, при которой разработчику остаётся
только решение по алгоритму, а состав файлов, конвенции и регистрация
соблюдаются автоматически.

Работа шла в plan mode: сначала картирование кодовой базы тремя параллельными
агентами (архитектура регистрации, конвенции/тестирование/CONCERNS.md,
внешний скилл `bim-auditor` в `MastermindServices`), план утверждён
пользователем, затем реализация.

## Что сделано

### 1. Автообнаружение вместо двух рукописных барреллей

`startup.py` и `tools/__init__.py` были ровно тем долгом, что описан в
[[Регистрация ведётся двумя рукописными списками]] — **этот долг закрыт**.
Проверено: ни один модуль `revit_mcp/` не импортирует другой модуль
`revit_mcp/` (все перекрёстные импорты идут в плоский `utils`), то есть
опасение «а вдруг порядок регистрации на что-то влияет» из того же файла
снято фактом, а не предположением.

- `startup.py`: `os.listdir` (не `pkgutil` — IronPython 2.7 плюс загрузка по
  UNC, предсказуемость важнее единообразия), поиск `register_*_routes` по
  regex, а не по имени файла (`rooms.py`→`register_room_routes`,
  `colors.py`→`register_color_routes` — соответствие не механическое).
- `tools/__init__.py`: `pkgutil.iter_modules`, та же логика.
- Оба файла сжались с ~60 строк рукописного списка до ~15 строк, которые
  больше никто не редактирует.

**Важное следствие для форка**: оба файла были ровно тем, что конфликтует при
каждом `git merge upstream/master` (репозиторий — форк
`Demolinator/revit-mcp-server`). Автообнаружение снимает и это.

### 2. Изоляция отказа — осознанное отступление от прежнего решения

`startup.py` раньше ловил все 22 регистрации одним `try` и перебрасывал —
это было записано как осознанное решение («расширение с половиной маршрутов
хуже, чем явно не загрузившееся»). При нескольких независимых разработчиках
расчёт меняется: чужая поломка не должна блокировать всех на всём парке.
Изменена **механика**, не намерение: `try/except` вокруг каждого модуля,
провал копится в новом `revit_mcp/registry.py`, `/status/` возвращает
`"health": "degraded"` и называет упавшие домены. Отказ не молчит, просто
не убивает соседей.

### 3. Тестовый уровень без Revit — закрыт приоритет №1

[[Тесты — это самостоятельные скрипты, а не pytest-сьют]] — теперь неполная
картина: добавлен `tests/unit/`, 233 теста, pytest как dev-only группа
(`pyproject.toml`), не попадает в деплой-payload.

Извлечён `revit_mcp/textutils.py` — `sanitize_string`/`normalize_string` без
импорта pyRevit, поэтому впервые тестируется под CPython 3. Регрессия
[[sanitize_string превращает кириллицу в вопросительные знаки]] теперь имеет
постоянный regression-тест вне Revit.

Конвенции из `CONTRIBUTING.md` (два рантайма, `ctx` последним, докстринг с
`Args:`, запрет `DB.ElementId(<int>)`, запрет `.IntegerValue`) вынесены в
`scripts/conventions.py` — единственный источник правды, на AST, не на
регулярках. Показательный урок в процессе: первая версия детектора f-строк
была на regex, ловила ложные срабатывания на `float("inf")`; вторая версия
гасила текст строковых литералов перед проверкой — и из-за этого **перестала
видеть настоящие f-строки** (f-строка — это `f"...{x}"`, гашение стёрло `f`
вместе со строкой). Финальная версия проверяет структурно:
`isinstance(node, ast.JoinedStr)`. Пойман собственным же тестом на детектор
(`test_f_string_detector_catches_a_real_f_string`), который до этого не
существовал бы, если бы проверки не тестировались отдельно от продукта.

`tests/unit/tool_manifest.txt` — теперь авторитетный список из 51 инструмента.
`deploy/gate.py` дополнен сверкой с манифестом: раньше проверял только
«инструментов больше нуля», пропавший домен проходил гейт молча.

Заодно найдено и исправлено: 10 инструментов с однострочными докстрингами без
блока `Args:` (детектор конвенций поймал сразу), включая два случая, где
докстринг **обещал** фильтрацию (`list_families` по `contains`/`limit`), а
маршрут в `revit_mcp/placement.py` эти параметры не читает вовсе — баг
реализации, не только документации, задокументирован прямым текстом в новом
докстринге. И двойная загрузка `revit_mcp/utils.py` под двумя identity в
`colors.py` (`from utils import ...` и `from .utils import ...` в одном
файле).

### 4. Приёмка инструментов без доступа к репозиторию

Ключевое архитектурное решение сессии, принятое пользователем в диалоге:
разработчики **не имеют доступа к репозиторию**, передают пакеты через папку
`inbox\` на общей папке, сборкой занимается пользователь.

Три слоя:

- **`contrib-kit/`** — самодостаточный набор на чистой stdlib (без `uv`, без
  `pytest`) с четырьмя командами: `new` (генерация каркаса), `check`
  (конвенции — та же логика, что у приёмки), `probe` (прогон обработчика на
  **собственном** Revit разработчика через `/execute_code/`, без клонирования
  репозитория), `pack` (сборка `.zip`). Включает адаптированный `AGENTS.md` и
  агент Kilo Code `.kilo/agents/revit-tool.md` — переписан под контекст «нет
  репозитория», не копия версии из корня.
- **`scripts/intake_package.py`** — приёмка на стороне пользователя: белый
  список файлов (ровно два модуля + манифест + заметки), отклонение при
  коллизии имён, статический скан опасных конструкций (`subprocess`, `eval`,
  `exec`, работа с файлами/сетью) — выносится на решение человека, не
  отклоняется автоматически, — и прогон полного `pytest` в изолированной
  копии дерева с применённым пакетом. Проверено на трёх пакетах: чистый принят
  (544 теста прошли), пакет с правкой `deploy/install.cmd` отклонён явно,
  пакет с `import subprocess` помечен и не пропущен молча.
- **`scripts/build_contrib_kit.py`** — копирует `scripts/conventions.py` в
  набор при сборке `.zip`, чтобы проверка у разработчика и приёмка у
  пользователя никогда не разошлись. Явно зафиксировано: набор нужно
  пересобирать при каждом изменении `conventions.py`.

Named limitation, зафиксированный текстом в трёх местах (`AGENTS.md`,
`INSTRUCTION.md`, README приёмки): автоматика **может только отклонять**,
одобрить может лишь человек, прочитавший код — принимаемый IronPython
исполняется внутри процесса Revit с полным доступом к API на каждой станции
отдела.

### 5. Исправлена ошибочная формулировка про GenproMCP

`deploy/install.cmd` отключал стороннее расширение `GenproMCP` с
комментарием про «route-name collision» — коллизии нет, у него
`routes.API('genpro_mcp')`, у нас `routes.API("revit_mcp")`. Пользователь
сначала попросил убрать отключение (раз коллизии нет), затем — вернуть
отключение (решение: один сервер, один канал раскатки). Итог: отключение
осталось, но обоснование переписано честно, и явно зафиксирован **принятый
разрыв** — `open_revit_server_model` (фоновое открытие `RSN://`-моделей с
закрытыми `#_RVT_LINK` worksets) ещё не портирован из `GenproMCP`, до тех пор
команда аудита открывает такие модели вручную.

### 6. Документация стала доступна клонирующему

`.planning/codebase/` (7 карт: `ARCHITECTURE.md`, `CONVENTIONS.md`,
`CONCERNS.md`, `INTEGRATIONS.md`, `STACK.md`, `STRUCTURE.md`, `TESTING.md`)
были в `.gitignore` целиком — теперь исключение только на `.planning/*`, а
`.planning/codebase/` явно разрешён. `CONTRIBUTING.md` и `AGENTS.md` — новые,
в корне репозитория (`AGENTS.md` читается автоматически Kilo Code, Cursor,
Windsurf, Claude Code).

### 7. Схема развёртывания (артефакт)

Существующая HTML-схема `https://claude.ai/code/artifact/919cc5b2-...`
(чертёжная эстетика, Oswald + IBM Plex) расширена Частью II для
разработчиков: три места кода (рабочая копия / опубликованные копии /
станция), что именно копируется белым списком, пять маркеров отслеживания
версии, и модель «пакет инструмента» вместо ветки+PR. По ходу дважды
исправлена по замечаниям пользователя: убран жаргон «шара» из технической
части (оставлен только в словарике с объяснением), приведены в соответствие
пути (`827_RevitMCP` без `src\`, как у пользователя, а не пример из README),
добавлено прямое объяснение «зачем вообще копия, если репозиторий и так на
общей папке» — вопрос пользователя показал, что это была самая неочевидная
часть схемы.

### 8. Инструкция по первичной раскатке

`deploy/SETUP-RUNBOOK.md` — 11 разделов от текущей структуры папок
пользователя до критериев приёмки пилота. Ключевые факты, подтверждённые
чтением скриптов, а не предположением: `MCP_SHARE_ROOT` в `config.cmd` уже
равен реальному пути пользователя (править не нужно); `install\` физически
появляется на сервере только после `publish-extension.cmd`; сборка требует
**pyRevit, установленный на машине публикации** (колёса ABI-привязаны к его
CPython, не к системному).
