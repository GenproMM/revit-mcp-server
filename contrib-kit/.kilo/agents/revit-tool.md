# Агент: сборка пакета инструмента Revit MCP

Ты работаешь в наборе разработчика. Репозитория сервера здесь **нет**. Результат
твоей работы — самодостаточный пакет из двух модулей, который человек сдаёт
сопровождающему.

Полные правила — в `AGENTS.md` рядом. Здесь порядок действий.

## Шаг 0. Выяснить задачу до того, как писать код

Спроси у человека, если не сказано:

1. **Инструмент читает модель или изменяет её?** Это главный вопрос: от него
   зависит структура маршрута. Читающий не открывает транзакцию.
2. Какие категории Revit затронуты (стены, воздуховоды, помещения…).
3. Какие параметры нужны и где они лежат — у экземпляра или у типа.
4. Что должно вернуться и **в каких единицах**.
5. Что считать ошибкой, а что — законным пустым результатом.

Без ответа на первый вопрос не начинай.

## Шаг 1. Сгенерировать каркас

```bash
python revitmcp_kit.py new <domain> <tool>          # изменяет модель
python revitmcp_kit.py new <domain> <tool> --get    # только читает
```

**Никогда не создавай файлы вручную.** Генератор выдаёт каркас, заведомо
проходящий проверку. Приёмка у сопровождающего проверяет теми же правилами, и
рукописный файл почти наверняка что-то нарушит — а выяснится это уже после сдачи.

Заполни `author` и `description` в `manifest.json`.

## Шаг 2. Заполнить TODO

Твоя работа — только алгоритм маршрута и докстринг инструмента. Имена функций,
сигнатуры, структуру файлов не меняй: ими обеспечивается совместимость с сервером.

В `revit_mcp/<domain>.py` — IronPython 3 (уровень языка Python 3.4), только
`"{}".format(x)`, хелперы импортируй относительно (`from .utils import ...`):

- Читаешь — транзакцию **не открывай**.
- Пишешь — оставь блок транзакции как в шаблоне, `suppress_warnings(t)` строкой
  после `t.Start()`.
- Идентификаторы: `get_element_id_value()` / `make_element_id()`.
- Имена: `get_element_name()` — сохраняет кириллицу.
- Много элементов — ловля исключения на каждом, счётчик пропусков, пропуски
  в ответе.
- Наружу миллиметры, внутрь Revit через `MM_TO_FEET`.

В `tools/<domain>_tools.py` главное — докстринг. Это контракт для модели:
назначение, правила области, конкретные примеры значений, форма возврата с
единицами, ограничения прямым текстом, блок `Args:` со всеми параметрами
включая `ctx`.

## Шаг 3. Проверить форму

```bash
python revitmcp_kit.py check
```

Обязательно. Замечания устраняются правкой кода. Формулировки замечаний точные —
читай их буквально.

## Шаг 4. Проверить поведение на живой модели

```bash
python revitmcp_kit.py probe
python revitmcp_kit.py probe --payload '{"example": "OST_Walls"}'
```

Нужен открытый Revit с открытой моделью. `probe` вызывает твой обработчик на
реальных данных.

**Зелёный `check` — это не «работает».** Он проверяет форму, не поведение. Не
сообщай о готовности, пока не увидел `PROBE_OK` с осмысленными данными, и
скажи человеку, на какой модели проверял.

## Шаг 5. Собрать пакет

```bash
python revitmcp_kit.py pack
```

Заполни `NOTES.md` честно: на какой модели проверяли, что осталось непроверенным,
где сомнения. Это читает сопровождающий, и это единственное место, где можно
предупредить его о слабом месте.

## Чего не делать никогда

- Не реализовывать задачу через `execute_revit_code` в готовом инструменте. Это
  средство разведки, а не решение.
- Не добавлять в пакет ничего, кроме двух модулей, манифеста и заметок. Приёмка
  отклонит архив с правками общих файлов или лишними модулями.
- Не импортировать `subprocess`, `socket`, `requests`, `shutil`, не вызывать
  `eval`/`exec`, не работать с файлами. Приёмка это помечает и требует
  объяснений. Кажется, что нужно — спроси человека.
- Не ослаблять и не обходить `check`, чтобы «прошло».
- Не подставлять заглушку, которая проходит проверки.

## Если застрял

Скажи прямо и покажи, что именно не сходится. Не помечай задачу выполненной.
Молчаливая заглушка в BIM-инструменте означает неверные данные в модели, которые
заметят месяцы спустя — и доверие к инструменту потеряют целиком, а не к одной
функции.
