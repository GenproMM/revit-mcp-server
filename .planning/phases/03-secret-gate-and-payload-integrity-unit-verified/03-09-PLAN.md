Close review finding WR-01, the one open item in 03-UAT.md. The user decided to fix it now, as a
separate gap-closure plan. A network share that drops after `_manifest.json` was read must never
be reported as tampering. Today it is reported that way: on Windows, CPython maps
ERROR_BAD_NETPATH (53) and ERROR_BAD_NET_NAME (67) to errno ENOENT. `_read_bytes` treats that as
"file absent", and `observe_tree` swallows an ENOENT on the `revit_mcp/` listing. Every listed file
then lands in `missing` and the verdict is `verified_mismatch`, which becomes a 423 once Phase 5
wires the check. Phase 5 also caches that verdict at load, so one SMB blip would block every
mutation until Revit restarts. This is a real deployment path: `deploy/install.cmd` sets
`EXTPATH=%SHARE%\ext`, so the extension loads from the share itself.

The fix: an observed absence counts as `missing` only once the reader has confirmed it. The
reader re-reads the manifest and gets the same parse, and only then reads each absent entry again
and gets ENOENT again. An absence that cannot be confirmed becomes `unverifiable` with the new
reason `absence_unconfirmed`. That mapping lives in `trust.evaluate_integrity`, alongside the rest
of the D-13 three-state mapping.

Purpose: restore the D-13 / ROADMAP SC6 / INTG-07 invariant, "a reference that is unreachable is
never reported as tampered", without masking a real deletion (INTG-02). INTG-02, INTG-03, INTG-07
and INTG-08 were Complete before this plan and stay Complete after it. This plan corrects the
implementation behind them. It adds no requirement and reopens none.

## Why this fix, and not the two options the reviewer sketched

The reviewer offered two directions. Both leave a hole that the required behaviours close.

- **Option A: after the scan, probe that `os.path.isdir(root)` and `os.path.isfile(manifest)`
  are still true.** This catches a drop that is still in progress at the probe. It misses an
  outage that ends between the scan and the probe: the files read as absent, the probe succeeds,
  and the false mismatch stands and is cached until Revit restarts. It also misses a republish
  that happens during the check.
- **Option B: treat a missing scope directory, or "every listed file absent", as unreadable.**
  This breaks the pinned `test_unreachable_absent_scope_directory_lists_its_files_as_missing`: on
  a reachable tree, a deleted `revit_mcp/` is a real total deletion and must stay a mismatch. It
  also does nothing for a partial drop, where some files were read before the outage, so required
  behaviour 3 (the mixed case) fails.
- **Chosen option C: corroborate each observed absence, in a fixed order.** First re-read
  `_manifest.json`. It must parse to a manifest equal to the first read, which also proves the
  root is still reachable. Only after that, read each absent entry again; it must be ENOENT again.
  If the manifest re-read fails, stop there: the absent entries are not touched, so a dead share
  costs exactly one extra open.
  - **Why the order matters.** Take any single outage, whatever its timing. If it is still going
    at the manifest re-read, that read fails, so the absence is unconfirmed. If it is over by
    then, the absent files read successfully the second time, so the absence is again
    unconfirmed.
  - **What still counts as a mismatch.** A real deletion on a reachable tree reproduces on the
    second read, so it stays a mismatch. Both pinned ENOENT tests keep passing unchanged.
  - **Cost.** No extra I/O on the matching path. No retries and no sleeps, so Revit's load is
    never stretched by a timer.
  - **What can still go wrong.** A false mismatch now needs two separate outages, one covering
    the first scan and one covering the re-read of the absent entries, with the share reachable
    for the manifest re-read in between. That is recorded as a residual below.

**On the reason code.** D-13 lists three `unverifiable` reasons. This plan adds a fourth,
`absence_unconfirmed`, under the same `unverifiable` state. The three states, the never-writes
rule and the D-15 423 body are unchanged. The orchestrator brief asks for an explicit reason code.
A distinct one also lets Phase 5's `/status/` tell "the share dropped during the check" apart
from a plain read error. If the user would rather keep D-13's reason list verbatim, the fallback
is a one-line change: map a non-empty `unconfirmed` to `read_error` in `evaluate_integrity`. This
is reversible, since nothing outside these two modules and their tests reads the reason yet.

## Residuals recorded, not closed (must appear in the integrity.py docstring and the SUMMARY)

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| integrity reader -> extension tree on a UNC share | inside the live Revit process at load; the share can drop, be republished, or be written by anyone with share write access |
| reader observation -> trust.evaluate_integrity | the pure mapping trusts only the observation shape it validates |
| integrity result -> Phase 5 /status/ and 423 | the result is cached at load and shown to engineers; it must carry no path or exception text |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-48 | Denial of service | `observe_tree` ENOENT on a dropped share read as missing, so verified_mismatch is cached and every mutation gets 423 until a Revit restart (WR-01) | high | mitigate | `unconfirmed_absences`: manifest re-read first, then the absent entries re-read; an unconfirmed absence is unverifiable/absence_unconfirmed. Share-drop, mixed and blip tests over ENOENT and winerror 53/67 (Tasks 1-2) |
| T-03-49 | Tampering (gate weakened) | an `unverifiable` result masking a real tamper | high | mitigate | Only entries read as ENOENT are ever re-examined, so a modified or added file is reported exactly as before. A real deletion on a reachable tree reproduces on the second read and stays a mismatch (`test_genuine_deletion_is_confirmed_by_a_second_read` and the three pinned tests). To turn a deletion into unverifiable, an actor must make the manifest re-read fail or differ, or restore the file within milliseconds of the scan. Anyone with share write access can already get unverifiable by deleting or corrupting `_manifest.json` (D-14 manifest_missing, existing behaviour) or can rewrite it to match (IN-03: a drift check, not a tamper defence). So the corroboration grants no new capability. The result is still visible as unverifiable, never verified_match |
| T-03-50 | Tampering (gate weakened) | mixed case: a file modified before the drop plus an unconfirmed absence gives unverifiable, not mismatch | low | accept | Same precedence as read_error since 03-04 (`test_unverifiable_unreadable_wins_over_a_modified_file`). It needs a real network failure coinciding with the load-time scan, and the next Revit start re-checks. Required behaviour 3 demands it |
| T-03-51 | Tampering (disk) | the reader writes, renames or deletes while corroborating | high | mitigate | Every new read goes through `_read_bytes` or `_list_names`, with no new `open(`. The AST write scan, the literal-`rb` test, `_guards` write guards and the before/after `_snapshot` in the share-drop tests |
| T-03-52 | Denial of service (Revit load) | the reader raises, or stalls Revit's load on a dead share | medium | mitigate | `check_integrity`'s existing try/except returns read_error (`test_unverifiable_when_the_corroboration_itself_raises`). There are no retries or sleeps. A failed manifest re-read short-circuits, so a dead share costs one extra open, and a matching tree costs none (`test_matching_tree_reads_the_manifest_once`) |
| T-03-53 | Information disclosure | a path, the share name or exception text leaking through the reason code or result | low | mitigate | The reason is the fixed constant `absence_unconfirmed`, and an unverifiable result carries empty lists. The `unconfirmed` entries stay inside the observation dict. `test_share_drop_result_carries_no_path_or_error_text` |
| T-03-54 | Tampering | corroboration opens a path a hostile manifest key named | low | mitigate | Re-reads come only from `absent`, which is built from paths that passed `valid_manifest_path`, plus the fixed `revit_mcp/` entry. The real-deletion record test asserts that the set of opened paths equals the first-pass set |
