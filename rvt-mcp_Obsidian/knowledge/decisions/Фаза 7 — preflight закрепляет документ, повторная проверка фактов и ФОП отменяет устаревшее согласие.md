# Фаза 7 — preflight закрепляет документ, повторная проверка фактов и ФОП отменяет устаревшее согласие

## Контракт

Реализованы планы 07-10 и 07-11. Факты для окна берутся внутренним read-only `/mutation_preflight/`, а не из догадок ассистента. Если документ не указан, его токен из успешного preflight закрепляется в final body и одноразовом permit.

Согласие относится к показанным фактам и политике. После accept сервер заново проверяет hash политики и получает preflight; digest включает токен документа и все возвращённые факты. Изменение либо провал повторного чтения запрещают мутацию (`facts_changed`). HTTP 400/404/412/503 от document guard запрещают вызов до окна (`preflight_refused`).

Пустой параметр экземпляра одного элемента может записываться без окна по D-10. Для добавления общих параметров требуются resolved GUID и точное имя (NFC, case-sensitive) в корпоративном ФОП. Недоступный источник — deny. После accept ФОП читается без cache; даже замена с сохранёнными mtime/size не проходит незамеченной повторной проверкой.

## Почему

Окно, основанное только на аргументах, не сообщает реальный масштаб записи типа. Согласие нельзя переносить на другой документ или на факты, изменившиеся за время ожидания.

## Границы доказанного

- Offline: 6860 passed, 3 skipped, cold start 1.016 с; реализация `ac11077`.
- Окно ограничено 1500 символами; большие пакеты показываются не полностью, но digest включает все факты.
- Preflight/recheck/send — не атомарная блокировка модели. Изменения между recheck и mutation остаются возможны.
- Чтение ФОП ограничено coroutine-дедлайном, но уже запущенное OS-чтение нельзя физически остановить.
- Публичный edit_family не экспонирует add_shared_parameters; этот seam проверен через тестовый MCP-инструмент и production bridge.
- Корпоративный файл, API Revit и Hermes UI ещё не проверены вживую: это 07-14, не основание объявлять фазу принятой или парк обновлённым.
