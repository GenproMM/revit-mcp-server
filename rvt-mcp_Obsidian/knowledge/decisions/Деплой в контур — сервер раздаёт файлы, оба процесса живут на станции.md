# Деплой в контур — сервер раздаёт файлы, оба процесса живут на станции

Пользователь попросил спроектировать раскатку этого MCP-сервера на отдел
в закрытом контуре компании (доступ к контуру — только по RDP, репозиторий
на сервере обновляет сам пользователь вручную).

## Решение

Централизованный MCP-сервер на самом сервере невозможен в принципе, а не просто
неоптимален. `revit_mcp/` — это pyRevit Routes **внутри процесса Revit**,
слушающий `127.0.0.1:48884` на рабочей станции конкретного инженера. CPython-
половина фиксирует `BASE_URL` один раз при импорте (`main.py:21-23`) — один
процесс `main.py` обслуживает ровно один `REVIT_HOST`. Централизованный
`main.py --streamable-http` потребовал бы per-request маршрутизации по хостам,
открытия Routes на `0.0.0.0` у всех станций и auth-слоя на обоих хопах — при
том что `/execute_code/` это неаутентифицированный RCE с полным доступом к
`doc`/`DB`/`clr`.

Поэтому **сервер — точка дистрибуции и обновления, не runtime.** Обе половины
исполняются на станции; сетевая шара только раздаёт и обновляет файлы.

## Архитектура доставки

```
СЕРВЕР \srv-dfs\...\827_RevitMCP\      (read-only для пользователей)
├─ revit-mcp-server\   git-рабочая копия (только админ; НЕ в путях поиска pyRevit)
├─ ext\...extension\   опубликованная обрезанная копия — pyRevit грузит с UNC
├─ payload\            CPython-половина, зеркалится на станцию
└─ install\            install.cmd, update.cmd, find-python.cmd

СТАНЦИЯ (только пользовательские права — без админа, без UAC)
├─ %LOCALAPPDATA%\RevitMCP\versions\<VERSION>\
├─ %LOCALAPPDATA%\RevitMCP\current  ──junction──> versions\<VERSION>
├─ %USERPROFILE%\.hermes\config.yaml      управляемый блок mcp_servers.revit
├─ %APPDATA%\pyRevit\pyRevit_config.ini   пишется ТОЛЬКО через pyrevit.exe
└─ триггер обновления при входе — задача планировщика, иначе автозагрузка
```

Обновления идут без действий пользователя: `publish-extension.cmd` на сервере →
подхватывается при следующем **полном** перезапуске Revit; `build-payload.cmd`
на сервере → подхватывается при следующем входе в систему (через триггер) плюс
следующий старт Hermes.

## Ключевой пересмотр решения: не свой Python, а Python из pyRevit

Первая версия плана бандлила автономный CPython (python-build-standalone) —
100+ МБ, работало и было проверено (гейт латентности 0.887с). Пользователь
поправил: pyRevit уже обязателен у всех и несёт с собой CPython
(`bin\cengines\CPY3123\python.exe`, embeddable-дистрибутив). Проверка на живой
машине подтвердила пригодность: 3.12.3, все нужные C-расширения на месте,
сервер поднимается на нём (0.826-0.938с, 51 инструмент).

Итог: payload **108 МБ → 34 МБ**, и снят риск AppLocker/EDR на неподписанный
`python.exe` в профиле пользователя.

Плата: embeddable-дистрибутив несёт `python312._pth`, который отключает `site`
и **полностью игнорирует PYTHONPATH**. Поэтому появился `deploy/server.py` —
точка входа, которую запускает Hermes: сам кладёт `app\libs` в `sys.path` и
передаёт управление в `main.py`. Файлы pyRevit не трогаются — его `._pth` общий
с движком pyRevit внутри Revit и перезаписывается при обновлении pyRevit.

Новая эксплуатационная обязанность: колёса под `app\libs` ABI-привязаны к одной
минорной версии CPython. `build-payload.cmd` пишет версию движка в
`payload\ENGINE`; `update.cmd` предупреждает о расхождении, `install.cmd`
падает с понятным текстом. **Обновление pyRevit со сменой движка = пересборка
payload** на сервере.

## Находки в процессе, не связанные напрямую с целью

- Планировщик задач Windows недоступен без прав администратора даже с
  `/RL LIMITED`, и в корневой папке задач, и в подпапке — подтверждено `access
  denied` и для `schtasks /Create`, и для `Register-ScheduledTask`. Запасной
  триггер обновления — ярлык в папке автозагрузки пользователя, без прав не
  требует ничего.
- `revit_mcp/status.py` отдаёт **503**, когда Revit открыт, но документа нет,
  а `_revit_call` в `main.py` схлопывает любой не-200 в строку. Наивная
  проверка «мост поднялся?» ждала бы полного таймаута против уже работающего
  Revit. См. [[get_revit_process_status различает Revit закрыт от Revit без документа]].
- `format_response` (`tools/utils.py`) при наличии ключа `message` возвращает
  **только его**, отбрасывая остальные поля успешного ответа. Собственный
  docstring `start_revit` обещал структуру, которой модель бы не получила, —
  переименовано в `outcome`/`next_step`.
