# get_revit_process_status различает Revit закрыт от Revit без документа

## Симптом

Новый инструмент `start_revit` (запускает Revit, если MCP-мост недоступен)
проверял готовность наивно: любой не-словарь от `/status/` считался «Revit не
работает». В живом тесте Revit 2027 стартовал по команде инструмента
(процесс поднялся, PID подтверждён), но проверка продолжала бы ждать до
полного таймаута — потому что `/status/` в этот момент отвечает не 200.

## Причина

`revit_mcp/status.py` возвращает **503**, когда `revit.doc` пуст (Revit открыт,
но нет активного документа — например, только что стартовал и стоит на Home
screen). `_revit_call` в `main.py` схлопывает любой не-200 в строку вида
`"Error: 503 - {...}"`. Разница между «сервер ответил, но не рад» и «сервер
вообще не отвечает» терялась.

## Фикс

`tools/process_tools.py:_bridge_state()` — трёхзначная проверка вместо
булевой: `ready` / `no_document` / `down`. Транспортный сбой распознаётся по
отсутствию цифрового кода сразу после `"Error: "` (`"All connection attempts
failed"`, `"timed out"`) — если код есть, сервер ответил, просто не 200.

`start_revit` считает запуск успешным уже на `no_document`: ждать, пока
документ откроется вручную, — значит ждать человека, а не Revit.

## Урок

Любая проверка «сервис жив?» через HTTP должна смотреть на код ответа, а не
только на факт связи — если транспорт схлопывает и то и другое в одну форму
(как здесь строка `"Error: ..."`), это нужно расшивать явно, иначе поллинг
будет ждать полный таймаут против уже поднявшегося сервиса.

Покрыто 22 детерминированными тестами с подставным мостом (Revit не
требуется) — `t_process.py` в скрэтчпаде сессии, не в репозитории.
